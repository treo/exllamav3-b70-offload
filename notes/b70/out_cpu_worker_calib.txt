CPU home (S_c) calibration past b=1 - compute-bound, so the planner's byte rate was never its currency
==============================================================================================================
ROLE, stated up front because it is easy to get backwards: in this design the PARENT is the 3090 (architecture
§2.1a: it also runs attention, the linear-attention states, the shared expert, the router and the sampler), and
the CPU cores are a separate HOME - `S_c` in `wall/layer = max(T_parent + S_g/936, S_b/rate_b, S_c/47.4)`.
What follows calibrates `S_c`, the leg this host can actually measure. The parent's own leg (t0 = 250 us/layer at
b=1, `S_g` at 936 GB/s) is NOT re-measured here and cannot be on this box, so the "binding returns to the parent
at b<=8" conclusion still rests on the inherited 3090 number; the close-out item worded "parent side past b=1" is
only partly addressable from this machine, and this file is the part that is.

Why this was on the list: plan_parent_budget.py charged the CPU home streamed bytes at CPU_RATE = 47.4 GiB/s while
the parent's fixed per-layer time (t0 = 250 us) sat on the 3090 leg. Neither had been measured above b=1, and the
placement decision turns on both.

Method: notes/bench_cpu_moe.py on real checkpoint tensors (Qwen3.8-Flash-Next-exl3-2.68bpw_h6_ng8, layer 5,
H=2560, I=640, K=2.5 effective, topk=10, 1.465 MiB/expert block, swizzle=1 wide=1, isa avx2=True bw=False
vnni=False - this host has no AVX-512/VNNI), uniform-random routing, torch threads pinned to 1 so the kernel's
own thread argument controls parallelism, min-of-n after 20 warm-up calls. Two regimes, distinguished by how
many experts are registered (L3 is 64 MiB = ~43 expert blocks):

  COLD      --experts 64 (94 MiB > L3): the timing loop cycles 64 different selection sets, so expert trellis
              bytes come from DRAM, like a real decode step over an unresident set.
  RESIDENT  --experts 16 (23 MiB < L3): every touched expert stays in L3 across the whole loop.

us/call (microseconds per MoE layer call) - threads = the kernel's thread argument:

  rows  thr    cold (64 exp, ~9-59 distinct)     resident (16 exp, ~7-16 distinct)
     1    4       1242.4                            1120.6
     1    8        656.0                             598.3
     1   16        392.1                             334.1
     2   16        701.3                             614.1
     4   16       1279.1                             923.8
     8   16       2273.3                            1602.1
    16   16       3678.0                            2996.3
     8    4       8197.6                            5705.8
    16    4      13427.3                           10714.5
  implied GiB/s on expert bytes, cold:  36.83 (r1) 37.89 (r2) 36.09 (r4) 31.66 (r8) 24.47 (r16), 16 threads
  implied GiB/s, resident:              34.79 (r1) 29.01 (r2) 24.72 (r4) 15.28 (r8)  8.20 (r16), 16 threads
  reference single-thread copy of a 0.49 MiB block: 37.6-38.9 GB/s read+write

WHAT THE DATA SAYS

1. The parent is compute-bound, not DRAM-bound, at every batch measured. Making the entire expert set L3-resident
   buys only 15 % at rows=1 (334.1 vs 392.1 us) and the implied byte rate does NOT rise when the data is warm -
   it FALLS (16 threads: 34.79 GiB/s warm vs 36.83 cold at rows=1; at rows=8, 15.28 warm vs 31.66 cold, because
   the resident run touches nearly the same bytes with fewer distinct experts and spends the time in arithmetic).
   A cache-resident workload achieving the same GB/s as a streaming one means bytes are not the limiter. This
   host has AVX2 without VNNI, so the integer mul1 path runs 128-bit lanes with the multiply-emulation the
   kernel uses; per-assignment cost is 39.2 us at rows=1 falling to 23.0 us at rows=16 (16 threads) - that is the
   real quantity the parent pays.

2. CPU_RATE = 47.4 GiB/s is not reachable by this kernel: the best observed is 37.9 GiB/s (cold, rows=2) and it
   degrades to 24.5 GiB/s at rows=16 as per-expert row count grows. Using 47.4 as a byte rate made the CPU home
   look ~1.3-1.9x faster than it is, and - worse - the direction of the error is batch-dependent, which is
   exactly the axis the placement decision turns on.

3. t0 = 250 us/layer is optimistic at b=1 and meaningless above it. Measured expert-only parent time at rows=1
   with 16 threads is 392 us cold / 334 us warm - and that EXCLUDES attention, router, norms and sampling, which
   the planner books separately. At b=16 the same kernel costs 3678 us for the layer's experts.

4. Batch scaling is favourable per token and brutal per call. Per token: 392 -> 230 us (16 threads, cold) from
   b=1 to b=16, because assignments/expert rise 1.06 -> 2.73 (the same expert serves more tokens). Per call:
   392 -> 3678 us (9.4x) because distinct experts rise 9.4 -> 58.6 and rows/expert rise too. Any statement of
   the form "the parent has X us of slack per layer" must therefore be re-derived per batch, not scaled.

5. Threads matter as much as batch: at rows=1, 4 -> 8 -> 16 threads gives 1242 -> 656 -> 392 us (3.2x). The
   parent's thread budget is a first-class planning variable, not an implementation detail - and the parent also
   owns the sampler and (in this design) attention, so 16 is an upper bound, not an assumption.

MODEL CHANGE ADOPTED (see plan_parent_budget.py): the CPU-home leg is booked as

     T_Sc(b, thr) = assignments x c(b, thr)          [ (token, expert) pairs x per-assignment cost ]

with c() interpolated from the measured table above rather than derived from bytes / CPU_RATE, and the byte rate
kept only as a floor (the max of the two). Profiles never benchmarked as a CPU home (GLM) keep the old byte model
and are printed as UNCALIBRATED rather than being lent Qwen's numbers.

CAVEATS, stated so the numbers are not over-read
  * Uniform-random routing. Real routing is skewed, which REDUCES distinct experts and so makes the parent
    cheaper than this table at b>1; the table is conservative in that respect and the size of the correction is
    unmeasured.
  * Single layer (5). Other layers differ in activation scale, not shape, so this should transfer; unverified.
  * The 3090 as parent cannot be measured on this host, so nothing here calibrates the CUDA-parent variant.
  * Warm-window again: the loop runs continuously (min-of-n after 20 warm-up calls), consistent with the rest of
    the chapter; no soak numbers here.
  * The resident regime used --experts 16 as a proxy for a pinned resident subset. A real parent with, say, 200
    experts pinned exceeds L3, so its behaviour sits between the two columns, closer to cold.

DID THE CORRECTION CHANGE ANY CONCLUSION? No - and that matters more than the 1.9x.
-----------------------------------------------------------------------------------------------
Re-running plan_parent_budget.py with the measured S_c leg against the previous byte-based table: every Qwen wall
moved by 0-1 us and no verdict flipped. At b=1/4/8 with 5/30/120 slots on the 3090, the old and new walls agree
(251/253/257 at b=1, 252/260/276 at b=4, 317/278/299 at b=8, reading the P_lpt column in both files), and the only movement is the LPT greedy shifting a handful of experts
off the CPU onto the B70 at low batch (e.g. b=1, 30 slots: 29/415/68 -> 29/425/58). The reason is structural: in
these configurations S_c is not the binding leg - the parent leg (T_parent + S_g/936) and the B70 leg are - so a
1.9x error in a non-binding term is invisible in the max().

So the honest summary is: the input was wrong, the units were wrong, and the answer did not move - because the
decision was made elsewhere. Where this correction WILL bite is any configuration that leans on the CPU home
heavily: the profile with the largest CPU residue in the table is GLM (172-197 of 288 experts homed to CPU at
b>=4, walls 1.3-5.4 ms/layer), and GLM has never been benchmarked as a CPU worker, so those rows are explicitly
labelled UNCALIBRATED and were deliberately left on the old byte model rather than being lent Qwen's per-assignment
costs. Calibrating GLM's shape (9 MiB/expert, topk=8, different K) is the next measurement that could change a
placement verdict.

STALE ITEM FOUND WHILE DOING THIS, not yet fixed: rate_b = 292.0 is the B70 byte rate and dates from the pre-rev-J
analysis. The adopted kernel measures 437-494 GB/s effective at rows=1-4 and 314 GB/s at rows=16 (out_revl.txt,
out_dpas.txt), and its per-launch times are tabulated in plan_decode_cost.py, which the placement planner does
not consult. Booking the B70 leg off a 292 GB/s constant is conservative but increasingly wrong; the fix is to
route that leg through the measured table. Left as the next task rather than changed silently here.
