plan_decode_cost.py - the measured B70 decode cost model that replaces "bytes / GB-per-second".

Why this module exists. plan_operating_point.py and plan_concurrency.py computed B70 decode time as
`expert_bytes / rate(matched footprint)`, sampling a rate curve measured with memcpy-shaped launches. That
model was retired by measurement: the real GEMV was instruction-bound for every kernel up to rev H, and its
time is independent of the quantization recipe (Qwen3.8 across K=2..6: 73.6-74.8 us for identical weight
counts,
b70-kernels.md 2b/2c). Two kernel families now exist, both bit-exact against a Python reference:

  dp4a   probe_gemv.cpp rev C with -DGEMV_KCONST  (compile-time trellis K)
  dpas   probe_dpas4.cpp rev G with DPAS_X=1      (tokens on M, experts in the grid)

and the engine dispatches between them by row count, which is why the tables below are indexed by rows.

Every number is microseconds per (expert, projection) on Qwen3.8@2.68bpw, E=10, measured as the reported
projection time divided by E, warm (>=15 s sustained load) and interleaved min-of-N, best split-K per
configuration. Two windows were kept where they disagree, because they sometimes disagree by 20 %:
see `SPREAD`. Cost is per weight, not per byte: these are the same weights at any trellis K.

Provenance: notes/b70/out_gemv.txt (rev C / KCONST), notes/b70/out_dpas.txt (rev F, rev G, DPAS_X, rev H, and
rev I = probe_dpas6.cpp, the current fastest at every measured point). Dispatch is by recipe as well as rows:
the DPAS families require K <= 5, so denser recipes fall back to dp4a.

cost spread note: two warm windows differ by up to ~20 % (rev G+X, down_proj, rows=1: 41.5 vs 50.9 us at E=10)

One kernel wins at every measured batch now: rev J (transposed tiles) beats rev I by 1.27-1.46x and
dp4a by ~8x at rows=16. Dispatch is a single family, with one caveat that is a design decision rather
than a tuning knob: rev J needs the device copy of the weights intra-tile permuted (dword q*K+i ->
i*8+q). Same bytes, same DRAM traffic, same output bits, ~1.5 ms one-time device permute for a 512 MB
resident set - but the device tensor stops being byte-identical to the checkpoint, which is the
property the 'native layout, no repack' constraint was protecting. If that constraint is kept
literally the fallback is dpas_gather (rev I) at +27-46%, still one kernel; dp4a is the only option
where no permutation is possible at all. Revs G/H carry no advantage now and remain for provenance.
Rows=2 is interpolated; nothing here extrapolates past the measured set 1/2/4/8/16.

Binding constraint now: rev J runs the gate projection at 437 GB/s effective (5.86 MiB in 14.0 us)
against measured ceilings of 484 GB/s (stream slope) and 674 GB/s (copy peak) - ~90% of the
achievable streaming rate, so decode is bandwidth-bound in the sense the earliest design notes
assumed, which no kernel in this line achieved until now. Its own diagnostics say balanced rather
than dominated: NO_MAD (12.5) sits above both FETCH_ONLY (8.9) and ALU_ONLY (10.9), and the
components sum to 21.3 against a full 14.0 (~35% overlap). The remaining levers are bytes and
locality - placement, ordering, the 18.35 GiB threshold - not instructions.

rows > 16 is outside the measured set; the DPAS path uses two M=8 fragments above 8 rows and its
cost slope is still rising at 16, so quoting a 64- or 256-token decode number from this table
would be an extrapolation, not a measurement.
