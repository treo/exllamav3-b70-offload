Instruction-count model, which is what actually explains these numbers
  The card issues ~256 EU x 2.8 GHz x 2 slots = 1.43e12 SIMD instructions/s; one 32-bit instruction
  covers 32 lanes, and at K = 3.0 each weight is 0.375 B of stream, so a kernel spending N lane-ops per
  weight tops out at 1.43e12 / (N x 2.67) bytes/s:
     N = 17 (rev A: address math + 64-bit shift + manual byte sum) -> 31.6 GB/s predicted, 27.9 measured
     N =  8 (rev B: grouped extraction + dot_acc byte sum)         -> 67.2 GB/s predicted, 61.4 measured
  Both within 10% of the model, and both FAR below the 250-292 GB/s that doc/port's decode budget
  assumed. Decode with a straightforward trellis GEMV is INSTRUCTION-bound, not bandwidth-bound:
  probe_rates walked the same bytes with ~1 op per weight and reached 292 GB/s, which is why it could
  never have detected this.

Rows scale badly, and CUDA says why. rev B still materialises byte-sums into SLM and then does
load+load+mul+add per (weight, row): at R = 8 the rate is 13.8 GB/s and at R = 128 it collapses to
0.2 GB/s (register spill from NB accumulators). exl3_gemv_int8_kernel.cuh never materialises byte-sums:
it keeps `prod = window * 0x83DCD12D` in a register and evaluates each row as ONE
dp4a_us(prod, splat(a_int8), acc) against activations pre-splatted to 0x01010101 * x8 in shared memory.
Per weight that is ~2 + R instructions instead of ~8 + 4R, and the same trick on Xe2 is
sycl::ext::oneapi::dot_acc(uint32, uint32, int32), which exists in this toolchain
(sycl/ext/oneapi/dot_product.hpp, plus mixed-sign vec<uint8_t,4>/vec<int8_t,4> overloads).
Next revision of this probe: drop the bs[] table, keep prod in registers, one dot_acc per (weight, row).

Ordering is NOT the lever at this instruction count - clustered/scattered ratios sit at 0.98-1.02 for
R = 1..32 - which is the honest reading of §3a and E4b: the locality win is real for the byte stream
(probe_rates 1.08-1.99x) but invisible until the arithmetic stops dominating.
