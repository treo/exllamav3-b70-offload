Instruction-count model, which is what actually explains these numbers
  The card issues ~256 EU x 2.8 GHz x 2 slots = 1.43e12 SIMD instructions/s; one 32-bit instruction
  covers 32 lanes, and at K = 3.0 each weight is 0.375 B of stream, so a kernel spending N lane-ops per
  weight tops out at 1.43e12 / (N x 2.67) bytes/s:
     N = 17 (rev A: address math + 64-bit shift + manual byte sum) -> 31.6 GB/s predicted, 27.9 measured
     N =  8 (rev B: grouped extraction + dot_acc byte sum)         -> 67.2 GB/s predicted, 61.4 measured
  Both within 10% of the model, and both FAR below the 250-292 GB/s that doc/port's decode budget
  assumed. Decode with a straightforward trellis GEMV is INSTRUCTION-bound, not bandwidth-bound:
  probe_rates walked the same bytes with ~1 op per weight and reached 292 GB/s, which is why it could
  never have detected this.

Rows scale badly, and CUDA says why. rev B still materialises byte-sums into SLM and then does
load+load+mul+add per (weight, row): at R = 8 the rate is 13.8 GB/s and at R = 128 it collapses to
0.2 GB/s (register spill from NB accumulators). exl3_gemv_int8_kernel.cuh never materialises byte-sums:
it keeps `prod = window * 0x83DCD12D` in a register and evaluates each row as ONE
dp4a_us(prod, splat(a_int8), acc) against activations pre-splatted to 0x01010101 * x8 in shared memory.
Per weight that is ~2 + R instructions instead of ~8 + 4R, and the same trick on Xe2 is
sycl::ext::oneapi::dot_acc(uint32, uint32, int32), which exists in this toolchain
(sycl/ext/oneapi/dot_product.hpp, plus mixed-sign vec<uint8_t,4>/vec<int8_t,4> overloads).
Next revision of this probe: became rev C below - drop the bs[] table, keep prod in registers, one
dot_acc per (weight, row).

Ordering is NOT the lever at this instruction count - clustered/scattered ratios sit at 0.98-1.02 for
R = 1..32 - which is the honest reading of §3a and E4b: the locality win is real for the byte stream
(probe_rates 1.08-1.99x) but invisible until the arithmetic stops dominating.

The numerics bug (eight rounds to localise, one line to fix): the HOST-SIDE activation splat.
    hspl = (int32_t)(int8_t)x * 0x01010101        // WRONG for x < 0
    hspl = (int32_t)((uint32_t)(uint8_t)x * 0x01010101u)   // byte-mask first, then multiply
Multiplying a SIGNED value by 0x01010101 does not replicate its byte. For x = -m it computes
-(0x0m0m0m0m) = 0x(255-m)(255-m)(255-m)(256-m), whose four bytes are (-m, -m-1, -m-1, -m-1): the borrow
from the negate charges one to each of the three upper bytes. Every negative activation therefore
contributed ~0.75 * bytesum too little, so the per-element deficit was 0.75 * (fraction of negative x) *
sum_k bytesum ~ -4.94e5 - near-constant in BOTH rows and columns, which is exactly why every "doubled
bias term" / "injected constant" reading of it was wrong. Two controls pin it beyond argument:
setting all activations to 0 made rev C exact (0/5120 mismatches), and setting them all to 1 also made
it exact - both are non-negative, so the buggy path never executed. CUDA builds splats with byte ops
(prmt / __byte_perm), never a signed multiply, for this reason.

Earlier fixes retained: the signed splat must be passed as int32_t to select the unsigned x signed
dot_acc overload (= CUDA dp4a_us), and the cross-subset reduce goes through SLM with a full
group_barrier because the device runs 16-lane sub-groups.

WHAT THAT MEANS, correcting the story this section replaces:
  1. The structural fix alone - prod in registers, one dot per (weight,row), no materialised byte-sums -
     is worth 1.8-3.3x over rev B at decode shapes. Peak decode rate is now MEASURED, not inherited:
     116.4 GB/s at E=512/R=1 (was assumed 150-180 from vendor comments).
  2. SPLIT-K IS NOT THE PARALLELISM CURE IT LOOKED LIKE. At E=10/R=1 - the sparsest realistic decode
     shape, 400 work-groups - ks=1 was the best configuration (80.2 us, 0.9% spread); raising ks only
     cost throughput. The E=10 deficit was rev B's per-item structure, not the grid size.
  3. Split-K pays exactly when row-tiling has already consumed the grid dimension: E=10/R=4 needs ks=4
     (x1.72) and at ks=1 rev C is actually SLOWER than rev B (x0.76). At E=96+ it never pays.
     So ks is a joint function of (E, tn, rows, M), not a fixed choice, and ks=1 is the default.
  4. Rows cost throughput roughly linearly in the accumulator count (116 -> 60 -> 31 GB/s for R=1/4/8 at
     E=512), consistent with the ~2+M instructions-per-weight model and against a bandwidth bound.

METHODOLOGY NOTE (why this section disagrees with the previous one): single medians at small shapes are
unusable. Identical E=10/R=1 configs measured 38.7, 45.7 and 52.5 GB/s in three back-to-back repeats,
and rev B's own spread at E=10/R=4 was 94%. The provisional "split-K recovers 5x at E=10" was drawn from
exactly that noise. Interleaving configs within each repetition and comparing minima (the estimator
probe_rates already used) gives 0.9-1% spread and reverses the conclusion.
