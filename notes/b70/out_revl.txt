rev L (probe_dpas9.cpp): the clean-line kernel — wins as the main path, no experiment switches
===============================================================================================
probe_dpas7.cpp had accumulated every hypothesis of the chapter (iselect vs gather, buckets, shared streams,
ablation modes, EPT sweeps, band defines, an address-debug print). It reads as a museum, and a museum is the
wrong shape for the kernel the engine is about to copy. rev L keeps the verified math verbatim and deletes
everything that lost. 1015 -> 726 lines; the kernel body has no mode variable and no compile-time experiment
flags left in the hot path.

KEPT (each is a measured win, referenced in the file header)
  * Tokens on M, weights as B, u8 x s8 -> int32 (rev G): XMX fixes N=16, so tokens belong on M.
  * ESIMD xmx::dpas with the unpacked tile in registers (rev H): no SLM, no barriers, no B loads.
  * Transposed tiles (rev J): operand routing becomes register rows with compile-time shifts.
  * One expert per thread (D4).
  * Partials + a SEPARATE combine kernel (D2: the atomic fused combine cost 4.5x the round trip it saved).
  * rows <= 16 (the spill-free ceiling from E29's ring sweep). Above that the engine buckets launches with the
    additive law; the probe does not carry the bucketing code any more.
  * gate+up in ONE launch as an argument (a second case dir), not an environment variable and not a second
    schedule: the same launch times both ways depending on whether dir2 was given.
  * 3 s of in-process warm-up by default (WARM_S overrides).

REMOVED (all refuted; implementations remain in probe_dpas7/8 for forensics)
  * DPAS_BKT / DPAS_SHARED row bucketing (E29) and the native NF=4 32-row launch.
  * DPAS_BUCKETS naive-schedule harness (the law is recorded; the harness is not needed).
  * DPAS_M override, DPAS_EPT override and EPT auto-fill, the four ablation modes, DPAS_ADDR_DEBUG, and the
    fused-vs-separate comparison scaffolding.
  * DPAS_CHECK specifically: rev J's self-check SKIPPED silently whenever the reference size mismatched the
    run, so its printed "pass" below rows=16 had never compared anything. rev L always writes its outputs and
    the harness (gate_dpas.py) does the checking.

VERIFIED IN EVERY MODE (bit-exact against each case's own y_ref; anchor rev I gate rows=1 = 19.4 us, healthy)
  native  rows=1  12.4 us | rows=16 19.4 us     (rev J published 13.7 / 21.3 in the same anchor window)
  fused gate+up KS=1: rows=1 22.6 us, rows=16 34.3 us  (E25a published 25.7 / 35.0)

THE 19 % THAT WASN'T THERE — a parameterization bug in my own probe, mistaken for a layout cost
------------------------------------------------------------------------------------------------
Verifying the clean kernel produced a measurement that contradicted out_e25_fuse.txt / out_rows_gt16.txt.
Gate, E=10, K=3, ks2, rows=16, min of 4 interleaved rounds, anchor 19.4 us:

  native   (transpose at load, tiles in (kt,nt) order)        19.40 us
  staged   (planar dwords, tiles in (kt,nt) order)            19.50 us   <- intra-tile transpose: free
  staged2  (planar dwords + band 2 = what AVX2 stages)        23.10 us   <- +19 %
  staged8  (planar dwords + band 8)                           23.20 us   <- +19 %, independent of g

Read literally that was a design problem: the parent swizzles tiles because it measured a 3.4x cold-traversal
win, the B70 would lose 19 % to the very same swizzle, and D3-alt ("copy the staged bytes verbatim") would need
a reordering pass at admit after all.

It was neither. Re-running the ORIGINAL rev J binaries (-DDPAS_STAGED_LAYOUT and -DDPAS_BAND=2 - the same
binaries the E25 sweep used) against rev L, on inputs whose provenance the gate establishes, all four arms
bit-exact, anchor 19.5 us:

  revJ  planar (band 0)     20.10 us      revJ  banded (band 2)     20.30 us   <- banding free, as recorded
  revL  planar (band 0)     19.60 us      revL  banded (band 2)     23.10 us   <- banding costs 19 %

Both measurements were right. The kernels differ in exactly one respect here: rev J read the band from
`#define DPAS_BAND`, so `kstride`, `estride` and `tbase` constant-folded; rev L read it from the `Launch` struct
at run time. Forcing rev L's band to a compile-time constant (same source, same bytes) gave 19.70 us for band 2
AND band 8 - the whole 19 % was my own runtime address arithmetic, not the data layout, not the hardware.

Final form: `Band` is a template parameter, `dispatch_band` specializes on {0, 2, 8}, and ONE binary serves
every staged form (anchor 19.5 us, all bit-exact):

  native 19.60 | staged 19.60 | staged2 19.20 | staged8 19.30 us

**Rule to carry into the engine: any parameter the admit path already knows belongs in the template parameter
list, not in a parameter block.** The gap is not free bookkeeping on this device - it was 19 % here, bigger
than several algorithmic wins this chapter recorded, and it hid in a struct field where no swept knob would
ever have exposed it. Candidates beyond `Band`: `K` (already templated), `KS`, and the shape constants
(`tn`, `tk`, `E`, `n`), which the engine knows per admitted tensor anyway since it compiles per shape.

Cost of the specialization, recorded honestly: probe build time 1.7 s -> 2 m 11 s (75 -> 225 device
instantiations). The engine does not pay that; it compiles one instance per admitted shape/band. The probe pays
it per rebuild.

Methodological footnote (same error class as LESSONS 42, third time): my earlier assertion that the E25 staged
arms were "bit-exact" had been read from `<case>/y_dev_*.bin` while those runs wrote into `<case>_planar` /
`<case>_full` - a vacuous verdict. Every check in this session reads the directory the run actually wrote, and
gate_dpas.py derives paths from the argv it passed. The original E25 dirs had already been regenerated by the
gate, so their bytes are unrecoverable; the resolution rests on the re-measurement above, not on the old
artifacts. Suspect your own harness first is now 12 deep.
