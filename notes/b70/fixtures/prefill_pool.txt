# The mul1 trellis specification

What an EXL3 tensor actually contains, written for someone implementing a new consumer of it.
Every numbered claim below is checked against real checkpoint data by
`python notes/verify_trellis.py` (branch history) — the tail-biting property, the exact match of
the independent NumPy dequantizer with `ext.reconstruct`, the codebook's value set, the packed
layout round-trips and the integer-fusion identity.

"mul1" is one of three EXL3 codebooks (`3inst`, `mcg`, `mul1`) layered on the same trellis
container. The container is what makes the format unusual: **weights are not stored as indices
into a codebook, they are stored as the 16-bit sliding windows of a bit ring**, and the codebook is
a pure function of that 16-bit window.

---

## 1. Tensor inventory of one quantized linear

A quantized `Linear` (dense, shared expert, or one routed expert) is a set of same-named tensors
next to the module key:

| tensor | dtype | shape | meaning |
|---|---|---|---|
| `<key>.trellis` | `int16` (read as `uint16`) | `(k/16, n/16, 16·K)` | the packed bit rings, one 16×16 tile per `(i,j)` |
| `<key>.suh` | `fp16` | `(k,)` | per input-channel scale (applied before the input Hadamard) |
| `<key>.svh` | `fp16` | `(n,)` | per output-channel scale |
| `<key>.bias` | `fp16` | `(n,)` | optional, per output channel |
| `<key>.mul1` / `<key>.mcg` | `int32` scalar | `()` | codebook marker; only its **presence** is read (`quantize.py:32`) |
| `<key>.su` / `<key>.sv` | `int16` bitfield | `(k/16,)` | legacy: packed ±1 sign bits, unpacked to `suh`/`svh` by `LinearEXL3.unpack_bf` |

`k`/`n` are the **padded** dimensions: `Linear` rounds both up to `pad_to = 128`
(`modules/linear.py:54-77`, and `BlockSparseMLP.intermediate_size_padded`), so `k/16` and `n/16`
are whole numbers of tiles and every dimension is a whole number of 128-wide Hadamard blocks.
Narrower runtime inputs are zero-extended to the padded width — this is the `hi != h_` padding seen
in the CPU offload path.

The bitrate comes from the tile width alone (`block_sparse_mlp_cpu.trellis_rate`,
`modules/block_sparse_mlp_cpu.py:381`, `modules/quant/exl3.py:67`):

```
K = tile_width / 16            # 16*K uint16 words per tile, always a whole number of words
integer 1..8 bpw  -> width 16, 32, 48, 64, 80, 96, 112, 128
half  1.5/2.5/3.5 -> width 24, 40, 56                (mul1 codebook only)
```

Observed in the shipped checkpoints (`notes/scan_widths.py`, `notes/scan_mixed_rates.py`):
Qwen3.8-Flash-Next @2.68 bpw stores routed experts at **2.5 bpw** (width 40) in layers 4-43 and at
**3 bpw** (width 48) in layers 0-3 and 44-47, its MTP head's experts at 2.5 bpw, its attention and
shared experts at 6 bpw, and `lm_head` at 6 bpw; Qwen3.5-35B-A3B @3.17 stores routed experts at
3 bpw, its MTP experts at 4 bpw, shared experts and attention at 7 bpw, `lm_head` at 6 bpw. Across
the whole local Qwen3.8-Flash-Next family the routed experts are uniform *within* every layer
(2.05/4.05/5.05/6.05 bpw quants use one rate everywhere; 2.68 mixes 2.5 bpw — layers 4-43 — with
3 bpw in layers 0-3 and 44-47; 4.18 mixes 4 bpw with 5 bpw in layers 0, 1 and 47). Rates therefore vary **per layer** (0.73 vs 0.88 GiB of expert trellis per layer, 36.33
GiB for the 48 MoE layers of Qwen3.8 @2.68), but every expert *inside* one layer shares a single
rate in all local checkpoints — which is what the staging byte layout assumes. The CPU worker
nevertheless keeps `bits`/`hb` per matrix (`MoeCpuMatrix`, `cpu/moe_mul1.h:24-41`), while
`register_layer`'s `proj_bytes` and `stage_phase` derive the per-expert block from **expert 0's**
dimensions (`moe_cpu_host.py:1158-1164`, `moe_mul1.cpp:3570`): a checkpoint that ever did mix rates
inside a layer would stage wrong offsets, so a port should assert uniformity at load rather than
rely on the observation. (An earlier revision of this note claimed layer 0 of Qwen3.8 @2.68 was
mixed; that was a scan artifact — the pattern conflated `model.language_model.layers.0` with
`mtp.layers.0`.)

## 2. The trellis container

Written by the converter as `quantize_tiles` → `pack_trellis` (`quantize.py:1117`), read by
`unpack_trellis` / `reconstruct` / the GEMV kernels. Per tile (256 weights):

* Position `i ∈ [0,256)` contributes `D(i)` new bits: `D(i) = K` at integer rates; at a
  half-integer rate `K = KA + 0.5`, `D(i) = KA + bit(i mod 16) of MASK`, `MASK = 0xAAAA`
  (alternating `KA`/`KA+1`, so every 16 positions consume exactly `16·KA + 8` bits).
* `S(i) = Σ_{j ≤ i} D(j)`, and the ring holds `R = Σ D = 256·K` bits.
* Position `i`'s **16-bit window** (its "state", the codebook index) is ring bits
  `[S(i)-16, S(i))`, read MSB first, indices taken `mod R` — a *tail-biting* ring: a window's low
  `D(i)` bits are its own new bits, its high `16 - D(i)` bits are the previous window's leftovers
  (`frac.cu:9-13`, `testlib/trellis.py:5-19`). Verified true on real expert tensors.
* Packed form: the ring as 32-bit words with ring bit 0 at the **MSB of word 0**, each word stored
  little-endian as two `uint16` (so `uint16[2j]` is the low half of word `j`).
* Element order inside a tile is *not* row-major: ring position `i` holds row-major element
  `tile_perm(i)`, the tensor-core fragment order

  ```
  for t in 0..31, j in 0..7:  r = (t % 4) * 2 + (j & 1) + 8 * ((j >> 1) & 1)
                              c = t // 4 + 8 * ((j >> 2) & 1)      # element = r * 16 + c
  ```

  (`quantize.py:44-68`, `moe_mul1.cpp:129-146`, `moe_unswizzle.cu:38-45`, `frac.cu:37-45` all
  encode the same permutation; `testlib/trellis.py:tile_perm` is the independent reference.)

So decoding a tile is: read the ring, take 256 overlapping 16-bit windows, map each through the
codebook, scatter with `tile_perm` into a 16×16 block.

## 3. The mul1 codebook (cb 2)

```
x(s) = (uint32)(s * 0x83DCD12D)                       # s = the 16-bit window
bytesum(s) = (x & 0xff) + ((x>>8) & 0xff) + ((x>>16) & 0xff) + (x>>24)
w(s) = fp16( (1024 + bytesum(s)) * k_inv + k_bias )   # computed as one hfma in fp16
       k_inv  = fp16 bits 0x1eee = 0.0067672729...    (~1/147.7)
       k_bias = fp16 bits 0xc931 = -10.388...         (= (-1024 - 510) * k_inv)
   ≡ (bytesum(s) - 510) * k_inv   in exact arithmetic
```

(`quant/codebook.cuh:36-50,80-104`; the multiplier is also the marker value stored in
`<key>.mul1`, `exl3_lib/quantize.py:19`.)

Measured properties (`notes/verify_trellis.py` section [3], on the full 65536-state space):

* `bytesum` takes 913 distinct values ⇒ **the codebook has 913 distinct weights**, up to 175 states
  sharing one value. Range `[-3.4531, 3.3477]`, mean `-0.0019`, std `1.0003`, and the 1/25/50/75/99
  percentiles (`-2.256, -0.699, -0.002, 0.695, 2.244`) sit within ~3% of the equivalent Gaussian's
  — i.e. the multiplication is chosen so that a uniformly distributed state maps to an
  (approximately) unit-normal weight. That is the entire design: the "codebook" is procedural
  (see `doc/procedural_codebook.png`), needs no table, and costs one multiply plus a byte sum.
* `mcg` and `3inst` decode differently — `(x & 0x8fff8fff) ^ 0x3b603b60` split into two fp16 halves
  that are added — and are **not** affine in a byte sum, which is exactly why the int8 fast paths
  (`EXL3_INT8_GEMV`, the CPU MoE kernels, unfused MGEMM) are mul1-only
  (`model/config.py:31,77-80`).

### 3.1 Why the CPU GEMV is a dot product of integers

Because `w` is affine in `bytesum`, a whole dot product collapses:

```
Σ_k w(s_k) · x_k = k_inv · q · ( Σ_k bytesum(s_k · M) · x8_k  −  510 · Σ_k x8_k )
```

with `x8 = round(x/q)` the row's int8 activations and `q` its scale
(`cpu/moe_mul1.cpp:36-56`). `Σ x8` is a per-row constant, so the weight-side term is one
`vpdpbusd` per 16 weights on AVX-512+VNNI, or (AVX2 / AVX-512BW, no VNNI) a bytesum-first
accumulate with `vpmaddubsw` + `vpmaddwd` that keeps the activation outside the byte pair to avoid
saturation. Accuracy is stated as ~0.9% per-call output RMS (GPU int8 GEMV mode-2 class); the
identity itself is verified numerically to fp16 rounding (`[5]`, rel err 3.3e-4).

Consequence for the input side: activations must be quantized to int8 per row, and a row whose
small elements would all round to zero is carried as **two** int8 rows (15-bit split,
`EXL3_MOE_CPU_WIDE`, `moe_mul1.cpp:76-82,393-420`). Accumulators are int32, which is why the CPU
kernel caps `k <= 8192` (`moe_mul1.cpp:3674`).

## 4. Layouts on top of the container: native vs "packed"

The **native** layout above is what every GPU kernel reads. The CPU expert kernels additionally
repack tiles so a GEMV's k-stream is sequential in DRAM. Rules are the single pair
`exl3_moe_cpu_swizzle_group(K)` / `exl3_moe_cpu_planar_layout(K)` (`moe_mul1.cpp:3633-3644`),
resolved by the runtime ISA tier (`EXL3_MOE_CPU_MAX_ISA` caps it) and per rate:

| tier | integer K | half-integer K | notes |
|---|---|---|---|
| `scalar` | native | native | |
| `avx2` (this test box: Zen 3) | band **2** + **planar** dwords, all K 1..8 incl. 8 | native | `avx2_swz2_pair` kernels |
| `bw`, `vnni`, `vbmi` | band **8**, except **K8 native** | band **8** | K8 routes to the dword kernel, which gains nothing |

Both transforms are pure index permutations of the tile array (and of the dwords inside a tile):

```
band-g:   tile (kt, nt) moves to linear index (nt / g) * tiles_k * g + kt * g + (nt % g)
              i.e.  out.view(tn/g, tk, g, words) = in.view(tk, tn/g, g, words).permute(1,0,2,3)
planar:   inside a tile (integer rates only), 32-bit dword w moves to  8*(w % bits) + w // bits
              i.e. the tile's (8, bits) dword grid is transposed to (bits, 8)
```

Applied by the worker's arena loader (`_copy_repacked`, `moe_cpu_host.py:394`, from
`rehome_trellis` in `_moe_cpu_child_main`), inverted host-side for demotions (`_copy_unpacked`),
and inverted **on the GPU after each DMA** by `moe_unswizzle_trellis` (`moe_unswizzle.cu`) whenever
a layer's experts arrive packed. Round-trips verified for K = 1, 2, 2.5, 3, 8 (`[4]`). Why planar
helps on AVX2: under the tensor-core permutation a half-row's 8 source dwords then sit in one
register, so a weight gather is one `vpermd` instead of a register walk
(`doc/env_vars.md:475-490`).

Effect on measured cold-expert bandwidth on this machine (Zen 3, `EXL3_MOE_CPU_*` defaults,
15 threads, 8-10 experts per call): K=3 with band-2+planar reaches ~47 GB/s, K=2 ~40 GB/s, while
K=2.5 — which the AVX2 tier leaves **native** — reaches only ~31 GB/s (`notes/m_cpu_*.txt`). A port
to an AVX-512 or NEON/SVE target inherits the band-8 rule instead, where half rates *are* banded.

`EXL3_MOE_CPU_SWIZZLE=0` keeps native bytes everywhere (loader, kernels and GPU path all agree,
since the rule is queried, not duplicated).

## 5. Turning a tile array into a weight matrix

```
Ŵ[k, n]                # rotated-basis weights: tile (kt, tn) -> block Ŵ[16kt:16kt+16, 16tn:16tn+16]
W = diag(suh) · (H ⊗ k-blocks) · Ŵ · (H ⊗ n-blocks) · diag(svh)      # H = Sylvester H_128 / sqrt(128)
y = x · W + bias
```

Applied in the order the kernels do it (`LinearEXL3.reconstruct_hgemm`, `MoeCpuHost._dq_linear`,
`testlib/moe.py:exl3_linear_ref`): scale the input row by `suh` and Hadamard-transform each
128-column input block; multiply by the rotated-basis `Ŵ` (from `reconstruct`); Hadamard each
128-column output block and scale by `svh`; add the bias. `had_r_128(input, output, pre_scale,
post_scale, scale)` is exactly "pre-scale → transform (÷√128) → post-scale" and requires the last
dimension to be a multiple of 128 (`quant/hadamard.cu:125-149`). `reconstruct_had_slice` folds both
Hadamards and the sign/scale vectors into the dequantized weights (the "folded" mode of
`EXL3_MOE_RECON_FOLDED`), which changes rounding.

The CPU kernels apply the same transform in fp32 (`transform_out`, `prepare_block`), which is why a
CPU/GPU parity test is statistical, not bit-exact.

## 6. Consumers to reimplement, and what each needs

| consumer | layout read | note |
|---|---|---|
| `exl3_gemv` / `exl3_gemm` / `exl3_mgemv` (dense Linear) | native | codebook templated `cb ∈ {3inst, mcg, mul1}`; int8-GEMV mode is mul1-only |
| `reconstruct` / `reconstruct_had*` | native | emits fp16 `Ŵ` (or original-basis W), used by all reconstruct tiers |
| `exl3_moe`, `exl3_moe_coop` (GPU fused MoE) | native | mul1 specialization is what enables the wide `N=128` tile instances and `EXL3_MOE_MTILE` |
| `moe_unswizzle_trellis` | packed → native | one read + one write per staged batch |
| `cpu/moe_mul1.cpp` (CPU MoE) | **packed** (per tier) | the only reader of packed bytes; dequant fused into int8 dot products |
| `ngram.cu`, `exl3_lib/ngram_codec.py` | native, different container | same codebook; per-row ring with a leading fp16 **scale word**, `1 + dim·K/16` words, 160-wide tail-biting rings and per-head bias |

Invariants a port must keep: tile is 16×16 weights; ring is `256·K` bits in `16·K` `uint16` words;
`uint16` pairs form big-endian-bit-order `uint32` words stored little-endian; window = 16 bits
ending at `S(i)`; element order = `tile_perm`; dimensions are multiples of 128 after padding;
`bytesum`-based decode is exact only for mul1. `tests/testlib/trellis.py` is a self-contained
NumPy/torch reference (pack, unpack, decode, dequant, dense linear) that the kernel tests treat as
ground truth — port the tests along with the format.

# B70 offload: harness

Continuous verification for the port: correctness, speed, and **utilisation** (board power, per the
brief: the best available indicator that the card is actually doing the work). It exists so that
every commit can answer three separate questions without ambiguity:

1. *Did the arithmetic change?* → levels A/B′ (kernel numerics, bit-exactness), independent of any
   protocol or model.
2. *Did the data movement or the protocol change?* → level D (liveness, ordering, geometry).
3. *Did the machine's work change?* → level E (per-hop, per-layer, per-token cost) and the power
   channel (which cannot lie about idleness).

Hygiene rules inherited from the prep work and enforced mechanically, because each of them once
produced a wrong conclusion in `doc/prep/measured-costs.md`:

* **pin placement state** per run (delete `~/.cache/exllamav3/expert_stats/<hash>.json`, or set
  `EXL3_MOE_CPU_SPLIT_STATS`, or redirect `block_sparse_mlp_cpu.EXPERT_STATS_DIR`) and print which
  start was used; the measured effect of forgetting this is +12–22 % on decode.
* **rotate expert selections** in any GEMV microbenchmark (working set ≫ L2's 18 MiB / L3's 64 MiB).
* **use real text** for anything routing-sensitive; random token ids wash the profile out.
* **state the measured link rate** with every bandwidth figure (sysfs is wrong on this box: it says
  `2.5 GT/s ×1` while carrying 14.4 GB/s).
* **report profiled runs separately** — `EXL3_SPLIT_PROF`/`HANDOFF_PROF` cost ~30 % by themselves,
  and on the B70 side `.wait()`-based instrumentation costs 24 µs per call (**[M]** `LESSONS` 1).
* **warm up** before timing — and a warm-up is measured in *executed device work*, not sample count. This device
  idles at 1200 MHz and needs ~40 ms of continuous work to leave it: the same kernel reads 44.0 µs after 200
  repetitions (still 1200 MHz) and 19.2 µs after 2000 (2000 MHz), plateauing at 19.1 µs by 20 000 reps (2650 MHz).
  Target >= 1 s of executed work (in the probes, `WARM_S`), take min/median over >= 4 interleaved rounds, and
  apply the rule to health checks too — an anchor polled with a 2 ms burst is measuring the idle clock, not the
  device. Read `xpu-smi stats -d 0 -j`'s frequency if a number looks off, before blaming anything else.

## Levels

### A — format, bit-exact (unchanged, plus two B70 checks)

### B′ — B70 kernel numerics (the new level)

The B70 kernel is a *new* implementation of an existing contract, so it is graded three ways at
once, on real expert weights:

| gate | bar | why |
|---|---|---|
| B′1 vs fp64 oracle | rel RMS ≤ **2.5e-2** per layer at rows 1/4/16 (the band the int8 scheme already occupies: the CPU path measures 1.45–2.16e-2) | the port must not change the numeric class |
| B′2 vs the CPU tier **at identical quantised inputs** | rel L2 ≤ **0.05** (the suite's `SCALAR_TOL`) | separating quantiser drift from GEMV drift; feeding both backends the same `x8/q/Σx8` is what makes this meaningful |
| B′3 vs the 3090 path | ratio to `reconstruct` ≤ ~25× | parity with Gate B2 |
| B′4 determinism | **bit-identical** over ≥30 repeated calls, and unchanged when the k-slice count changes for the same shape | catches the atomic-accumulation mistake §3 of `b70-kernels.md` |
| B′5 quantiser parity | the CUDA-side and B70-side quantisers (`QUANT_INPUT=1` vs `2`) agree **bit-for-bit** on the same fp16 rows | cheap, and it has historically been where Hadamard normalisation bugs hide |
| B′6 codebook vectors | the K=4 cheat-sheet table (state / product / byte-sum / weight for six `(r,c)` pairs incl. the wrap case `(0,0)`) and `bytesum ∈ [0,1005]` over all 65536 states, run *on the device* | the shift-by-32 and tail-biting traps are silent-corruption bugs |
| B′7 no spills / one dp4a | `zeKernelGetProperties` → `spillMemSize == 0 && privateMemSize == 0` for every shipped kernel × rate; ISA dump shows a single instruction for the dot | Recipe B's whole premise is register residency |

Scripts: `notes/b70/acceptance_kernel_b70.py` (mirrors `notes/acceptance_kernel.py`, adds the
fixed-input B′2 mode and dumps the quantised tensors it used).

| invariant | test |
|---|---|

| the engine never calls `.wait()`/blocks on the job path | an instrumented build counts blocking calls and asserts zero during a generation; a regression here costs 24 µs/layer silently |

| no PCIe poll storm | assert round-trip latency of the T2 loop stays ≤ 2× the single-poller baseline while N groups are parked (`probe_resident.cpp` as a regression test) |
| **homes are disjoint** | no expert may be resident on both devices at once: `tests/b70/test_placement_disjoint.py` asserts `S_g ∩ S_b = ∅` from the placement tables *and* that each device's local id mapping is injective; a replication bug would silently double capacity use and make every capacity number in the report meaningless |
| a spanning row combines in a fixed order | the 3090 → B70 → CPU add order is deterministic and B′4-style bit-repeatability survives it; a row spanning all three homes is an explicit fixture, not an accident of routing |
| B70 VRAM accounting | upload + scratch accounted in the memory planner; `-mba` never over-commits; unload frees everything (no leak across reload) |
| queue/region lifetime | `unregister_host_memory` on unload; a second load in the same process re-registers cleanly |

### E — performance floors

Every gate below is a *floor or ceiling on a measured quantity*; "explained by a mechanism from
E1–E5" is an acceptable outcome, "within noise" is not (see the hygiene rules at the top).

| gate | reference / floor | note |
|---|---|---|

# MoE CPU offload: measured costs

Every number in the companion documents (`moe-cpu-offload-data-paths.md`, `tuning-knobs.md`) that
looks like a duration comes from here. Raw logs are in `notes/m_*.txt`, produced by the scripts in
`notes/` (`bench_cpu_moe.py`, `bench_handoff.py`, `bench_link.py`, `prof_e2e.py`, `run_e2e.sh`,
`geom.py`); rerun them to reproduce. They are dev scaffolding, not part of the library.

## 0. Machine and method

| | |
|---|---|
| GPU | NVIDIA GeForce RTX 3090 (sm_86, 24 GiB), one device, `torch 2.14.1+cu130` |
| CPU | AMD Ryzen 9 5950X, 16 physical / 32 logical cores, 2 CCD × 32 MiB L3, **AVX2 tier only** (no AVX-512/BW/VNNI/VBMI) |
| DRAM | 125 GB, dual-channel DDR4 |
| Link | PCIe **Gen 4 × 8** (sysfs `current_link_speed=16.0 GT/s`, `current_link_width=8`, max `x16`) — `notes/bench_link.py` |
| Driver state note | with the GPU idle the link reports Gen3; it trains to Gen4 x8 under load and stays there |

Models: `/home/treo/projects/vendor/tabbyAPI/models/Qwen3.5-35B-A3B-3bpw-hq2` (40 MoE layers,
256 experts, top-8, H=2048, I=512, experts at **K=3**) and
`…/Qwen3.8-Flash-Next-exl3-2.68bpw_h6_ng8` (48 MoE layers, 512 experts, top-10, H=2560, I=640,
experts at **K=2.5** in most layers). Qwen3.5 is small enough to also load entirely on the GPU, so
it provides an all-GPU reference for the same weights.

Method notes / caveats:

* Wall-clock (`time.perf_counter`) around host calls; CUDA **events** for device-side spans; the
  torch profiler (`notes/prof_e2e.py`) for per-kernel self time.
* The worker is run *in-process* by `notes/bench_handoff.py` via the bound
  `exl3_moe_cpu_worker_run` (same entry point the child process uses), on a real pinned
  `SharedMemory` segment built by `tests/testlib/moe_handoff.py`. Numbers therefore exclude
  process-spawn and pipe effects but include everything else.
* Cold-expert discipline: the CPU-GEMM sweep rotates over 64 different random expert selections so
  the trellis bytes are not served from the 64 MiB L3. A single repeated selection measures ~2×
  faster and is meaningless.
* Both `EXL3_SPLIT_PROF` and `EXL3_MOE_HANDOFF_PROF` add per-layer cost of their own: the profiled
  run measured 67 tok/s where the same configuration without profilers measured 93-98 tok/s
  (§8). Treat the *ratios* inside those logs as indicative, their absolute levels as inflated.
* `notes/prof_e2e.py` feeds **random** token ids, so its routing (and therefore how many experts
  cross `stream_t` in the prefill measurement) differs from real text: the profiled prefill streamed
  3 571 of 7 680 CPU experts. Where a byte count matters it is recomputed from the
  `EXL3_MOE_STREAM_DEBUG` batch lines of the same run (`notes/m_prof_e2e_sd.txt`).
* **Placement history leaks between runs.** Dynamic placement writes a per-model expert-frequency
  profile at unload and reseeds from it at load, keyed only on model dir + expert count. Every `-mcs`
  number in §8 after the first is therefore "warm"; §8.3 quantifies the effect (+12-22% decode) and
  gives the controlled comparison. Use `notes/run_profile_ab.sh` as the template for clean A/Bs.
* Everything here is one AVX2 host + one Ampere GPU. Sections marked *(arch)* are the numbers that
  will move on a different CPU tier; the protocol for re-measuring is the point of the harnesses.

|---|---|---|
| 1 (empty job) | **20.2-25.6 µs** | 13-19 µs/layer |

Reading: the layer cost is (experts touched × expert bytes) ÷ (CPU stream rate) plus a ~20-35 µs
handshake+enqueue tax, and it is *identical* whether jobs are pipelined or serial, i.e. at these
sizes the worker is saturated by one job and gets no benefit from queue depth. An all-`-1` job
costs 20 µs, which is the floor any port must beat or match.

With `EXL3_MOE_MEMOPS=0` the same Qwen3.5 rows measure 171.9 / 285.9 / 507.4 / 977.9 / 1982 /
4240 µs (`notes/m_handoff_nomemops.txt`) — within noise of the memops numbers, because the ~190 µs
of compute dwarfs the ~4 µs difference in handshake cost (§3). The knob only matters for layers
where the CPU job is small, i.e. mostly cold tails.

**Cross-check of the copy path (P1', whole-layer mode).** Its per-job cost isn't measured as a
single number, but composes from §2: at 1 row it is the `int32` cast + up to two pad kernels
(~3 µs each, GPU), three D2H `copy_` at the latency floor (3.5-4.7 µs each), the `done` wait, the
H2D readback (4.7 µs at 8 KiB) and four flag memops ≈ **26 µs of device work**, against 20 µs for
the fused path's two kernels — which is exactly what the fused path was written to remove
(`block_sparse_mlp_cpu.py:573-574`). At a full 64-row chunk it is 21.6 + 41.3 + ~4 × 4 ≈ **90 µs**, on
jobs whose worker compute is ~2 ms (§4) or more.

That composition predicts the end-to-end numbers: in `-mcl 40` mode nothing but the shared expert
overlaps the worker, so a token should cost `40 × (compute + copy overhead)` on top of the all-GPU
time — `40 × (220 + 26) µs ≈ 9.8 ms` + `8.5 ms` ≈ **18.3 ms/token = 55 tok/s**, measured 54.5
(§8). Likewise `-mcl 20` (half the layers offloaded) predicts `8.5 + 4.9 = 13.4 ms ≈ 75 tok/s`,
measured 78.4.

B70 prefill: what changes when the weights are resident, and the one kernel that has to exist for it
=====================================================================================================
Status: **in scope** (operator direction). This note replaces the "non-goal" disposition this chapter first
wrote for architecture.md §12 row "DPAS route R1 vs R2", and it exists because that row's gate - "E4/E7 prefill
sweep at 32/128/512 rows" - names an experiment no kernel in this tree can run: `probe_dpas9` supports M ≤ 16
rows per launch, and everything larger is row-bucketing, which E29 measured as **additive in weight traffic**
(x2.00 / x2.98 / x3.96 at 32 / 48 / 64 rows, `out_rows_gt16.txt`).

1. WHY THE OLD "PREFILL IS DEAD FOR S_b" CONCLUSION DOES NOT DECIDE THIS
   That conclusion was about *streaming/staging* weights from the host per chunk over the link (measured 13.3
   GB/s pinned→device, 16.3 GB/s staged memcpy, ~175 µs/job, port-acceptance E5) - a byte/rate argument that
   applies when the card cannot hold the expert set. A B70 holding routed experts changes the traffic model
   outright: prefill then reads **weights once per chunk** and streams only activations (R × H × 2 B per layer
   per chunk, ~40 MB at R=2048 on Qwen3.8, vs ~786 MB of weights). The relevant sentence in
   `out_concurrency.txt` is still true - "the binding quantity for prefill is the same one as for decode: bytes
   per layer per step" - but with residency the bytes-per-layer term is a constant (E × expert_bytes), so
   prefill cost per TOKEN falls in proportion to chunk size, which is exactly the behaviour the plan said the
   B70 could not have.

2. MEASURED INPUTS (all from this tree, nothing assumed)
   FIRST, A UNITS CORRECTION to the version of this note that cited "272 rows". That figure is
   (367e12/2 MAC/s) ÷ 674e9 B/s = 272 **MAC per byte**, which belongs to 1-byte-per-weight formats.
   Trellis weights are 0.375 B each and the integer-DPAS route spends 4 MACs per weight-token
   (kernels.md §2c item 13b), so the arithmetic-intensity bar is 4/0.375 ≈ 10.7 MAC/byte and the
   **eligibility crossover is ~26 rows/expert at the 674 GB/s copy peak, or ~59 at the 292 GB/s this
   GEMV family actually achieves** (kernels.md §4 says exactly this; this note had it wrong).

   Rows per expert at realistic chunks, from the LIVE traced routing (`profiles/live/live_268.json`,
   mean over 48 layers; the stored profile said something much worse - see the last bullet):
       R= 512: mean 10 rows/expert; 10.4% of experts ≥ 26 rows, and they carry 75.0% of the picks
                                          (4.3% / 51.4% against the stricter 59-row bar)
       R=2048: mean 40 rows/expert; 24.3% of experts ≥ 26 rows, carrying 94.3% of the picks
                                          (15.8% / 85.6% against the 59-row bar); hottest ≈ 1,029 rows
       R=8192: mean 160 rows/expert; 40.2% of experts ≥ 26 rows, carrying 100% of picks
   So the honest statement is the opposite of "prefill is bandwidth-bound, the kernel does not need the
   matrix unit": **a minority of experts per layer carries nearly all the work, and those experts are
   already past the XMX bar at every chunk size worth running.** The design consequence is per-expert
   tiering (kernels.md §2c item 2: tile height ≤ rows/expert, `MS_=4` vs `MS_=1` because a 64-row tile
   "wastes ~60/64 rows" at small M), not one kernel for the whole chunk.
   Under the STORED profile the same R=2048 / 59-row test qualifies 0.4% of experts carrying 0.6% of
   picks - i.e. the flat routing profile had been quietly arguing AGAINST building the prefill path, and
   it was the wrong input (out_live_trace.txt), which is the second time this week that input changed a
   build/no-build decision.
   * Weight bytes per layer, from the census (`out_placement.txt`): Qwen3.8@2.05 599 MiB, @2.68 750 MiB,
     @4.05 1.17 GiB, @5.05 1.47 GiB, @6.05 1.76 GiB, GLM@3.05 2.53 GiB; B70 usable 31.9 GiB against expert
     sets of 28.1 / 36.3 / 56.3 / 70.3 / 84.4 GiB. **Residency is the first constraint, not the kernel.**
   * Decode-side rates the same kernel family already achieves: 437 GB/s effective (rev L, small resident set,
     partly L2), 492 GB/s at E=96 rows=1, 287-292 GB/s at E=96 rows=16 (`out_quant_ladder.txt`); copy peak
     674 GB/s; sustained power caps the box near 285 W with DRAM at ~54% of peak (`out_sustained_power.txt`).
   * Kernel-shape constraints that any prefill route inherits: 128 GRF/thread budget, and M>16 per thread
     spills 1,856-3,584 B/thread to scratch (E29); a work-group may hold at most 64 work-items for kernels of
     this register footprint (E25c's `Total number of work-items in a work-group cannot exceed 64`); SLM is
     128 KiB per group and a group-scoped barrier is free (−0.03…+0.22 µs, `out_e25c_groupscoped.txt`).

3. THE ARITHMETIC, WHICH SAYS WHY THE KERNEL MATTERS MORE THAN THE ROUTE
   Bucket amplification, computed on the live routing (each touched expert's bytes re-read once per 16-row
   bucket, Qwen3.8@2.68, equal bytes/expert, mean over 48 layers):
       R= 512 -> 2.24x      R=2048 -> 7.01x      R=8192 -> 26.29x
   (support caveat: "touched" is the 205.7 experts the 192-token trace ever selected, so the true tail -
   experts with small but non-zero p - dilutes these slightly downward; the numbers are per-layer means.)

   Per MoE layer for one 2048-token chunk, Qwen3.8@2.68 (750 MiB of expert weights):
     weights read ONCE      750 MiB → 1.17 ms/layer at 674 GB/s  →  56 ms/chunk → 36.6k tok/s
     weights read 7.01x    5.26 GiB → 8.2 ms/layer               → 393 ms/chunk →  5.2k tok/s
   Compute ceiling for the same chunk (48 layers, 3 projections, the 4-MAC-per-weight-token integer route):
   ~2.2 ms/layer → 105 ms/chunk → 19.2k tok/s, i.e. **the bucketed kernel sits at 1/7 of the memory roof and
   still below its own compute ceiling - the worst of both**, and the gap widens with chunk size (26.29x at
   R=8192). So the prefill case for the B70 is decided by one property: does an expert's weight bytes get read
   once per chunk, or once per 16 rows? **Measurement answered this: once per 16 rows, and it does not matter.**
   Two escapes were built and tested — co-resident row slabs (`probe_gemm`) and rows-deep items that read each
   tile once (`probe_xmx`) — and neither beat 16-row launches (1.47x / 2.01x worse at 32 / 64 rows for the
   latter), because the constraint at these shapes is register pressure and device fill, not bytes
   (`out_probe_gemm.txt`, `out_probe_xmx.txt`). Read the amplification table below as a **capacity and energy**
   statement, not a time statement.
   For GLM the arithmetic is harsher in capacity and gentler in traffic: 2.53 GiB/layer cannot be resident on
   one 31.9 GiB card across 42 layers (106 GiB), so prefill there is a residency-policy question first - and
   its rows/expert at R=2048 is ~2048×8/288 ≈ 57 mean, ≈ 4 buckets today. GLM has no live trace, so unlike
   Qwen3.8 its hot-tail share (§2's 94%-of-picks number) is unmeasured, not small.

**3a. MEASURED AT REAL CHUNK SIZES** (`out_prefill_scale.txt`; E=512 so weights per projection = 251 MiB =

    1024         770.8             210.9                   4856                3.71x
    2048        1396.5             382.1                   5360                6.72x
    4096        2683.1             734.1                   5580               12.90x

The byte model and the measurement agree: §3's one-read roofline of 36.6k tok/s divided by the measured 6.72×

R·topk/16 — so larger chunks do not help much; only lowering the amplification does, and the two mechanisms that
could (rows-deep items, SLM staging) both measured worse, leaving **co-scheduled slabs at 9–16 %** as the only

4. THE DESIGN THAT AVOIDS THE SPILL — SUPERSEDED BELOW by `probe_slm` measurements; read §4a as the design
   Register pressure is what caps M at 16, so do not raise M per thread. Keep **an expert's B tile resident in
   SLM and loop its row-slabs inside the kernel**: each work-item still computes a 16-row slab (the shape that
   provably fits 128 GRFs), but the weights come from SLM instead of DRAM, so the DRAM traffic per chunk is
   one read per expert regardless of how many slabs the expert needs. Group budget: 64 items × (B fragment
   registers + 16-row accumulator) is the same footprint that already works at decode; SLM at 128 KiB/group
   cannot hold a whole expert (Qwen3.8 gate is 0.49 MiB), so B is staged per K-chunk and the K-loop, not the
   M-loop, drives SLM turnover - the traffic question is whether a K-chunk's B bytes are re-read per M-slab
   from SLM (cheap, on-chip) rather than from DRAM (the failure mode we are removing).
   Named experiment (call it `probe_gemm.cpp`, decode-probe lineage, same timing protocol):
     * shapes: real Qwen3.8@2.68 gate/up/down tiles at E ∈ {10, 96}, rows/expert ∈ {16, 32, 64, 128};
     * variants: (A) today's bucketing, as the control; (B) SLM-staged B, M-slab looped, integer/u8 operands
       (**route R2**); (C) same but B dequantised to fp16 on load (**route R1**);
     * the measured quantity is **effective weight bytes per chunk** (derive from G-w/s × K ÷ 8, the chapter's
       convention) not just µs, because the whole question is traffic amplification;
     * pass: ≥437 GB/s effective AND ≤1.15× one-read traffic at rows/expert = 64; fail: traffic scaling with
       ⌈rows/16⌉, which means the route is settled but the mechanism is wrong;
     * R1-vs-R2 discriminator: their ALU costs differ (R1 pays dequant per load: 4 unpacked bytes → fp16;
       R2 keeps the integer domain and scales in the epilogue, which D6 already requires contraction-safe) but
       their DRAM traffic is identical, so at rows/expert ≤ 105 - where §2 says prefill lives - **the routes
       should be indistinguishable and the choice is dequant ALU headroom**, measurable as the delta B-vs-C at
       fixed traffic. That is a much cheaper question than the one §12 posed, and it is answerable at
       rows=32/64, not 512.
   Constraint to design around, already measured: 64 work-items per group. At 16-row slabs that is 1,024 rows
   of M coverage per group per K-chunk - comfortably above the 105 rows/expert the measured distribution
   needs, so the cap is not the binding term for prefill (it was, decisively, for E25c's cross-dependency
   fusion, where one group had to cover a whole expert's tiles).

**4a. WHAT MEASUREMENT SAID (probe_slm, `notes/b70/out_prefill_gemm.txt`) — the SLM mechanism above is
   refuted outright; what replaces it is a HYPOTHESIS, not a measurement.** With identical ALU per dword and,
   after the ISA showed the first comparison was scalar-vs-vector, identical `load.ugm.d32x4` widths in all
   three modes:
     * **SLM staging is 1.44× / 2.51× / 6.03× slower** than reading globally at 20 / 40 / 80 KiB per group,
       degrading as the staged region grows. The ISA gives the mechanism: the same walk costs 1177 instructions
       instead of 719, because staging adds 89 `store.slm` plus 80 `load.slm` on top of the 80 global loads it
       was meant to replace. No scratch traffic in any mode, so this is not a spill story — and to keep the
       accounting honest, the two 40 KiB bodies here spill comparably (256–320 B of `%scratch`, 10 scratch
       loads / 8 stores each), so spills are not the differentiator either.
     * I also wrote that concurrent global re-reads are *cheaper* than unique reads (1689 vs 1348 GB/s of
       unique bytes at 40 KiB; 1581 vs 1130 at 80 KiB). **Retracted as a measurement** — see the CONFIDENCE
       block in the artifact: both probe bodies turn out to be dominated by scalar address arithmetic (149
       `add`, 100 `shl` against 32 vector loads) and the reuse mode does 32× the loads per iteration for a
       near-identical time, which is math-bound behaviour, not memory-bound. It remains a reasonable
       *hypothesis* (and matches llm-scaler's group-major rule 4), to be tested by `probe_gemm`.
   Scope note on the refutation: the probe reads SLM with a per-lane strided vector pattern. A layout designed
   for SLM broadcast — llm-scaler's linearized `asyncCopyTile<AOS,true>` layouts — might not show this, and
   that is untested; what is tested is that *my* proposed staging shape is a non-starter, and the fact that
   llm-scaler went to real trouble over AOS layout is consistent with SLM being easy to misuse.
   Design that follows: **(expert, column tile, k-slice) → work-group**, **(16-row slab) → work-item**, one
   launch per chunk, B read from global exactly as decode does it today. No staging pass. The E25c cap of 64
   work-items/group allows 1,024 rows of M coverage per group against the ~105 rows/expert measured, so the cap
   is not binding here (unlike E25c's cross-dependency case).
   This also *explains* E29's additive bucket law instead of contradicting it: buckets are separate launches,
   so by the time bucket 2 revisits an expert far more than L2 has streamed past and the reuse distance is
   gone. Same bytes, same kernel, different co-scheduling — which is why the fix is a mapping change.
   The experiment list above stands with one amendment: variant (B) becomes the group-mapped global-read kernel
   (not SLM-staged), and the pass criterion stays traffic-based (≤1.15× one read per expert per chunk at
   rows/expert 64) with the ISA checked for scratch. The failure mode to watch for is a kernel that puts row-
   slabs in successive iterations of *one item's* loop — that recreates the bucket pattern's reuse distance
   inside a single thread and will look correct while paying 7×.

# MoE CPU offload: the data paths

Scope: every path a token's activations and an expert's weights take when routed experts run on
the CPU, for both offload modes, plus the CUDA-side work each path performs. Companion documents:
[`tuning-knobs.md`](tuning-knobs.md) (what each knob changes about these shapes),
[`measured-costs.md`](measured-costs.md) (measured cost of each hop),
[`mul1-trellis.md`](mul1-trellis.md) (the weight format the CPU kernels read).

Everything below is anchored in the tree at HEAD (`cdc785db`, v1.6.5). File:line references are
given so each claim can be checked. Machine-readable geometry is reproduced by
`python notes/geom.py` (kept in the branch history).

---

## 0. Participants

| Piece | Where | Role |
|---|---|---|
| Forward thread (parent) | `exllamav3/modules/block_sparse_mlp.py::BlockSparseMLP.forward` | routing, tier selection, enqueues all GPU work |
| Split/offload mixin (parent) | `exllamav3/modules/block_sparse_mlp_cpu.py` | decides *which* path per layer per step, hands tensors to the host |
| Handoff host (parent) | `exllamav3/model/moe_cpu_host.py::MoeCpuHost` | owns the pinned shared-memory region, job rings, slot views, VRAM rings, copy streams |
| CUDA handoff kernels | `exllamav3/exllamav3_ext/routing.cu` (`moe_split_issue_kernel`, `moe_split_collect_add_kernel`, `moe_split_map_kernel`), `exllamav3/exllamav3_ext/cpu/moe_handoff.cu` (flag ops, fused issue/collect, worker loop) | publish/consume flags, move bytes between VRAM and pinned slots |
| Worker process (child) | `moe_cpu_host.py::_moe_cpu_child_main` + `cpu/moe_handoff.cu::exl3_moe_cpu_worker_run` | owns expert weights in a huge-page arena, computes GEMVs, stages weights for GPU streaming |
| CPU expert GEMM | `exllamav3/exllamav3_ext/cpu/moe_mul1.cpp` | mul1 trellis dequant fused into int8 dot products |
| GPU expert paths | `exllamav3/exllamav3_ext/quant/exl3_moe*.cu`, `reconstruct.cu`, `moe_unswizzle.cu`, `hgemm*.cu`, `libtorch/blocksparse_mlp.cpp` (`bc`, bsz ≤ 8 fused decode) | everything the GPU still computes |

Two independent module-level switches choose a path (they are not env knobs):

* `BlockSparseMLP.cpu_offload` — whole layer's routed experts live on the CPU (`-mcl`).
* `BlockSparseMLP.cpu_split_first` — a tail slice `[first, E)` of every eligible layer's experts
  lives on the CPU (`-mcs`); `cpu_split_first` is also the base of the worker's expert numbering.

They are mutually exclusive (`cpu_maybe_offload_load` / `cpu_maybe_split_load` assert it), so
exactly one is set per module.

Within a path the choice is by row count `bsz = y.shape[0]`:

```
                          bsz < stream_min_rows (32)          bsz >= 32
                          ─────────────────────────           ──────────────────────────
split (-mcs)              P1 fused decode handoff             P2 prefill (memcpy jobs), or
                                                            P3 streamed prefill when experts are hot
whole layer (-mcl)        P1' copy-path issue/collect         P2 / P3 (same functions)
```

`bsz < 32` also covers speculative-verify batches (`stream_min_rows` happens to equal the graph
batch cap `TEMP_ROWS_GRAPH = 32`; they are independent constants). The child never knows which mode
produced a job: both feed the same job ring.

## 1. Shared memory: what all paths have in common

One `multiprocessing.shared_memory.SharedMemory` region per worker (per model component: main /
draft / MTP), page-locked in the parent with `cudaHostRegister(..., PORTABLE | MAPPED)`
(`moe_cpu_host.py:1050` `_register_handoff`), so the GPU can read/write it directly under UVA.
`gpu_base_ptr` (`cuda_host_get_device_pointer`) is the device-visible alias; all kernel-facing
addresses are computed from it.

*Lifecycle*: `Model.load` spawns the child process **before** loading any module (`model.py:614-616`)
so the worker's own interpreter/torch/checkpoint-index startup overlaps the GPU-side load — note that
`moe_cpu_host.py`'s module docstring still says the child is spawned at the first layer registration.
Layers are then streamed to the child over a pipe (parent→child via a sender thread, child→parent
acks and arena-chunk descriptors), the region is created and the worker's `ready` flag is awaited in
`ensure_started` on the first forward, and a host watchdog thread starts there. Tensor-parallel loads
raise `NotImplementedError` if an offload was requested (`model.py:695-710`): the TP loader exports
modules from CPU-staged tensors, which would silently drop the offload.

```
offset 0        ctrl block:  quit | pass_wake | abort | ready | jobs_tail | jobs_head   (64 B apart)
offset 384      MoeJob jobs[256]            (1056 B each: 7 u32 header + experts[256] + seq_hi)
offset 270720   flags: data_ready[8] | done[8] | consumed[8] | stage_done[8] | pinned_free[8]   (64 B stride)
offset 273280   stage ring tail/head
offset 273408   MoeJob stage_jobs[64]
offset 340992   compute slot data, num_slots x slot_size            <- MOE_CTRL_SIZE
        +n*slot  weight-staging slots, num_wslots x wslot_size       <- wstage_off (sent in "start")
```

Flag width: 32-bit on CUDA (compared cyclically by `cuStreamWaitValue32`), 64-bit on HIP (its wait
is a plain unsigned `>=`, so 32-bit flags would satisfy early after wrap). Both cases own a 64-byte
cache line; the descriptor carries the sequence as two 32-bit halves.
Constants: `MOE_JOB_RING 256`, `MOE_MAX_SLOTS 8`, `MOE_MAX_WSLOTS 8`, `MOE_STAGE_RING 64`,
`MOE_JOB_MAX_EXPERTS 256` (`cpu/moe_handoff.h:54-60`).

Slot geometry comes from the registered layers, not from the model (`ensure_started`,
`moe_cpu_host.py:1187`):

```
max_hi   = max(spec.hi)      # k of gate/up  = the hidden width the experts were quantized at
max_ho   = max(spec.ho)      # n of down     = the width of the routed sum
max_topk = max(spec.topk)
off_x   = 0
off_sel = align64(cap_rows * max_hi * 2)          # fp16 x    [cap_rows, max_hi]
off_w   = align64(off_sel + cap_rows * max_topk * 4)   # i32 sel [cap_rows, max_topk]
off_out = align64(off_w + cap_rows * max_topk * 2)     # fp16 w  [cap_rows, max_topk]
slot_size = align64(off_out + cap_rows * max_ho * 4)   # fp32 out[cap_rows, max_ho]
```

All `hi`, `ho`, `topk` must be equal across registered layers (assert at
`moe_cpu_host.py:1200`), otherwise the D2H/H2D copies would be strided — torch implements those
with a host-side staging pass performed *at enqueue time*, outside stream order, which would ship
the slot's previous contents.

Concrete numbers (Qwen3.8-Flash-Next, `H = 2560`, `topk = 10`, defaults `num_slots = 4`,
`cap_rows = 64`): `x` 320 KiB, `sel` 2.5 KiB, `w` 1.25 KiB, `out` 640 KiB, `slot_size` 963.8 KiB,
4 slots = 3.76 MiB; plus 2 × 32 MiB weight-staging slots and 333 KiB of control ⇒ ~68 MiB pinned
per worker (`region=68.1 MiB` in the harness logs).

Job kinds (`MOE_JOB_KIND_{COMPUTE,STAGE,COMPUTE_GATED}`, `cpu/moe_handoff.h:56-70`): a
`COMPUTE_GATED` job's payload may be entirely `-1` (no CPU-resident expert selected), and then both
the worker's compute and the collect's readback are skipped — the common case once the split tail
is genuinely cold.

## 2. P1 — fused decode handoff (split mode, `bsz < 32`)

Entered at `block_sparse_mlp.py:1138` (`cpu_split_submit`) with
`y (bsz, H) fp16`, `selected_experts (bsz, topk) int64` **holding raw router ids**, `routing_weights
(bsz, topk) fp16`. `submit_issue_fused` returns `None` when `bsz > cap_rows` or either tensor is
non-contiguous, and the caller falls back to P1' (copy path).

One Python call per half, each doing host + GPU work in one extension entry point. Timeline of one
decode step, one layer (`│` = idle/in another activity):

```
parent stream : …router │ issue-kernel → data_ready ───────► [GPU experts (bc.run_bszN)] → [shared expert] │ wait done → collect-add → consumed │ …
worker pool   :  (spinning on jobs_tail)  │ spin data_ready │ GEMV gate+up │ GEMV down │ done ───────┘
                                        ▲ descriptor written by the host *before* the stream ops above
```

The waits are stream memory operations, so they occupy no SMs and cost ~1.8 µs of host enqueue each
(`measured-costs.md` §3); the parent never blocks. If the worker finishes before the GPU reaches the
collect, the wait retires immediately and the layer costs nothing but its two kernels.

**Issue** — `MoeCpuHost.submit_issue_fused` (`moe_cpu_host.py:1411`) →
`ext.exl3_moe_split_issue_fused` (`cpu/moe_handoff.cu:245`):

1. Host: refuse if the job ring is within 4 of full (caller throttles on `jobs_head` and retries);
   write the descriptor into `jobs[tail % 256]` (`kind = COMPUTE_GATED`, `slot`, `rows`, `topk`,
   `seq` halves), then release-store `jobs_tail`.
2. Stream: if the slot has a previous tenant, `cuStreamWaitValue32(consumed[slot] >= prev_seq)`.
3. Stream: `moe_split_issue_kernel<<<1, 1024>>>` (`routing.cu:1165`) — a **single block** — which
   * translates router id → physical slot in place (`map` mode; also bumps the hit histogram with
     `atomicAdd`), and writes the worker-space id (`p - first_cpu`, or `-1`) straight into the
     pinned slot's `sel` with zero-copy stores;
   * writes `dev_count[slot] = 0/1` (whether any pick was CPU-resident);
   * if none: `__threadfence_system()` and return — **no activation traffic at all**;
   * else copies `w` (`rows*topk` halves) and `x` (`rows × hi` halves, zero-padded from `h_` if the
     module's hidden width differs from the quantized width) as `int4` stores.
4. Stream: `cuStreamWriteValue32(data_ready[slot] = seq)`.

Why the translate is **in place**: the bsz-1/bsz≤8 routing outputs are static tensors whose
addresses are baked into the BC (bound-class) kernel graphs that run the GPU-resident experts, so
the physical-slot remap must update those buffers rather than produce new ones
(`routing.cu:1101-1106`, `block_sparse_mlp_cpu.py:592-608`). Note also that this handoff cannot be
captured into any replayable graph: step 1 writes a *host* descriptor whose sequence number changes
per call and advances a ring index, and the waits reference per-slot flag lines by value. The model
forward is eager Python enqueues; only the expert kernels themselves (`bc`) are pre-captured.

Data volume for a decode step, per offloaded layer: `sel` `topk×4 B`, `w` `topk×2 B`, and either 0
or `x = hi×2 B` per row. On Qwen3.8 at bsz 1: 40 B + 20 B + 5 120 B (or nothing). Measured: the two
kernels cost 3.9 and 4.0 µs of device time, the pair of host calls ~14-22 µs to enqueue, and a job
whose selection is all `-1` costs 20-26 µs end to end (`measured-costs.md` §4, §6).

**Between issue and collect** the caller enqueues its own GPU expert work (so it overlaps the CPU):
`bc.run_bszN` for the GPU-resident experts (bsz ≤ `MAX_BSZN = 8` fused decode kernel), and the
shared expert(s) (`block_sparse_mlp.py:1436`, only for `bsz <= MAX_BSZN`).

**Collect** — `MoeCpuHost.submit_collect_fused` → `ext.exl3_moe_split_collect_fused`
(`cpu/moe_handoff.cu:295`):

1. Stream: `cuStreamWaitValue32(done[slot] >= seq)`.
2. Stream: `moe_split_collect_add_kernel` (`routing.cu:1298`), grid = `ceil(rows*h_/1024)` blocks:
   reads `dev_count[slot]`; if 0 it exits (no PCIe reads); else
   `final_out[row, c] += *(volatile float *)(h_out + row*ho + c)` — the fp32 partial is folded
   **directly out of pinned memory**, no H2D copy, and the add is in place into the routed sum.
3. Stream: `cuStreamWriteValue32(consumed[slot] = seq)` — published *after* the readback on the
   same stream, because the slot's next tenant may issue from a different device.

**Worker side** (`cpu/moe_handoff.cu:351` loop): spins on `jobs_tail` (hard spin 65536 `pause`
iterations, then 50 µs naps; `pass_wake` — bumped by `MoeCpuHost.begin_pass` at the top of every
forward — resets the backoff and primes the thread pool), pops the job, spins on `data_ready[slot]`,
scans `sel` for any ≥ 0 (full count only when handoff profiling is on), runs
`exl3_moe_cpu_forward_raw` (§5), release-stores the job's seq into `done[slot]`.

## 3. P1' — copy-path issue/collect (whole-layer offload at decode, and the fused path's fallback)

`_issue_compute` (`moe_cpu_host.py:1469`) is the general, un-fused form. Per `cap_rows`-row chunk
of the batch:

1. `sel32 = selected_experts.to(torch.int32)` (GPU cast, whole tensor once).
2. `y_pad = F.pad(y, (0, hi - h_))` if the widths differ (GPU), plus an `rtmp` readback buffer when
   `ho != h_`.
3. Host writes the descriptor (`kind = COMPUTE`, i.e. **not** gated: the collect always reads the
   slot back) and bumps `jobs_tail`; throttles against ring overflow with a 200 µs host poll loop.
4. Stream: `wait consumed[slot] >= last_seq`, then three contiguous `copy_(!non_blocking)` D2H:
   `slot.x[:n] ← y_pad[a:b]` (`n×hi×2 B`), `slot.sel[:n] ← sel32[a:b]` (`n×topk×4 B`),
   `slot.w[:n] ← routing_weights[a:b]` (`n×topk×2 B`); then `data_ready = seq`.
5. Deferred (`submit_collect` → `_collect_one`): `wait done >= seq`; H2D
   `slot.out[:n] → out[a:b]` (`n×ho×4 B`, or via `rtmp` then a GPU slice-copy when `ho != h_`);
   `consumed = seq`.

Whole-layer offload uses this for both halves: `cpu_offload_issue`
(`block_sparse_mlp_cpu.py:610`) issues before the shared expert runs and `cpu_split_combine`
collects afterwards, so the shared expert's kernels cover part of the CPU's latency. Since
`kind = COMPUTE` the slot is always read back and, with `cpu_partial` as the *only* contribution,
`cpu_split_combine` replaces `final_hidden_states` rather than adding to it.

Multi-chunk behaviour: the issue loop keeps at most `num_slots` jobs in flight and inline-collects
the oldest one before reusing its slot. Without that window the deferred collect's `consumed` write
would sit behind the same stream's `consumed` wait (deadlock; the "second-prompt freeze").

## 4. P2/P3 — prefill

`submit_prefill` (`moe_cpu_host.py:1864`) is entered when `bsz >= stream_min_rows` (32). It first
counts assignments per expert **on the GPU, then reads them to the host once**:

```
shifted = flat + 1                          # -1 sentinels (GPU-resident picks) land in bin 0
counts1 = zeros(E+1); counts1.scatter_add_(0, shifted, ones)
counts_h = counts1.tolist()[1:]             # <- the only host sync before the tail compression
streamed = [e for e in range(E) if counts_h[e] >= stream_t]
```

* Nothing streamed, or the layer cannot stream (`rows < 32`, no `expert_bytes`, expert block larger
  than a weight-staging slot, or no aux tensors) → **P2**: plain `_issue_compute` + `_collect_compute`
  over the whole batch (`submit`), i.e. `ceil(rows/cap_rows)` jobs of §3, up to `num_slots` deep.
  Data volume scales linearly: `rows × hi × 2 B` down, `rows × ho × 4 B` back up.
* Something streamed → **P3** (`_submit_prefill_streamed`, `moe_cpu_host.py:1976`).

P3 shapes the work as follows (still one call, no further syncs — everything after `tolist()` is
host-known):

1. `order = argsort(flat)`, `token_sorted = order // topk`, `weight_sorted`; prefix offsets `offs[]`
   built from the host counts, so every expert's token segment is a slice.
2. **CPU tail**: mask streamed assignments to `-1`, compress to the rows that still carry work
   (`tidx`), then `_issue_compute` on the compressed rows — *issue only*. So the tail's D2H volume is
   `n_tail × hi × 2 B` with `n_tail ≤ rows`, typically much less.
3. Per staged batch of `per_slot = min(wslot_size // expert_bytes, batch_experts, 256)` experts, on
   a **separate copy stream** with a `num_wslots`-deep ring:
   * *pinned arena* (`EXL3_MOE_PINNED_ARENA=1`): the parent DMAs each expert's contiguous
     `[gate|up|down]` block straight out of the worker's arena mapping
     (`arena_views[chunk][off:]` → `vram_slots[ws]`), `exp_b` bytes each. No worker involvement.
   * *staged*: a `STAGE` job in the second ring; the worker's dedicated stager thread waits
     `pinned_free[ws] >= prev_seq`, `memcpy`s the same expert-major packed layout
     (`stage_phase`, `moe_mul1.cpp:3570`) into the pinned weight slot, and sets `stage_done[ws]`.
     The copy stream waits that flag, then `vram_slots[ws] ← wviews[ws][:used]` (`used = len(batch)
     × exp_b`), and publishes `pinned_free[ws]`.
4. If the CPU tier stores the weights packed (see `mul1-trellis.md` §4), `restore = True` and the
   copy stream runs `moe_unswizzle_trellis` per projection over the whole batch
   (`moe_unswizzle.cu`, grid `(tiles_k × tiles_n/8, num_experts)`, 128 threads), producing native
   order in a **second** VRAM ring (`native_slots`, allocated only for layers whose experts arrive
   packed). The GPU kernels never see packed bytes.
5. `wready_ev[ws]` recorded; compute stream waits it; the batch is computed by one of three tiers
   (§4.1). `wconsumed_ev[ws]` recorded on the compute stream, gating the next writer of that slot.
6. Tail jobs are collected last (`_collect_compute`), then `out.index_add_(0, tidx, out_t)`.

### 4.1 The three streamed compute tiers

Per expert, by assigned count `c` (all thresholds in tokens/rows, not bytes):

| tier | condition | what runs | data |
|---|---|---|---|
| fused | `c <= stream_fused_t` (256) and layer eligible (`hi == ho == h`, no biases, silu/gelu/relu2) | `ext.exl3_moe` over the batch's cool experts, one launch per row-tile tier (16/32/64 rows, `mtile`) | pointer tables (9 lists × batch) built **on the host** from `vslot.data_ptr() + bi*exp_b`, uploaded once; temp buffers `(C, stream_fused_t, H/I)` fp16 |
| batched reconstruct | `stream_fused_t < c <= recon.max_rows` | `moe_batch_recon.run_group`: one host→device meta copy (ids/starts/counts/3 pointer lists), one pointer-table reconstruct + one strided-batched `hgemm` + one Hadamard launch **per projection** per group of ≤ `EXL3_MOE_RECON_BATCH` experts, rows gathered into and scattered out of a slab padded to the group's largest expert | dequant scratch `w_scratch` (`k*n` fp16), padded slab `(B·cmax, …)` |
| per-expert reconstruct | everything above, or when the batched tier is unavailable (biases, `EXL3_MOE_STREAM_BATCH_RECON=0`) | `_dq_linear` × 3: `had_r_128` → `reconstruct` → `hgemm` → `had_r_128` (+bias), `_act`, then `out.index_add_` | gathered `xg = y.index_select(0, idx)`, `w_scratch` fp16 (k,n) |

Tier 1 reads the native-order trellis tiles directly (the bytes restored in step 4, or the staged
ones when the layer's rate is unpacked); tiers 2/3 first dequantize to fp16 weights (`k × n`), so
their traffic scales with `k·n`, not with rows.

Eligibility of the whole streamed path additionally requires `spec["expert_bytes"] <= wslot_size`
(one expert must fit a slot) and that the layer's `suh`/`svh` (and optional biases) were fetched to
the GPU at load (`aux`, `block_sparse_mlp_cpu.py:746`).

## 5. Inside the worker: one compute job

`exl3_moe_cpu_forward_raw` (`moe_mul1.cpp:3801`), given `sel[rows×topk]` (worker-local, `-1` = skip)
and the row-major fp16 `x`:

1. Zero `out` (`rows × H` fp32).
2. Bucket `(token, weight)` by expert; split each bucket into chunks of `MAX_M = 4` rows.
   `nc = Σ_e ceil(|e| / 4)` chunks; a decode job with `topk = 10` distinct experts is `nc = 10`.
3. Workspace per chunk: `tin` (fp32 `MAX_SLOTS × k`), `splat32`/`splat_dup` (int32 `MAX_SLOTS × k`),
   `splat_pair` (int32 `MAX_SLOTS × k/2`), `tout_g/u` (`MAX_SLOTS × I`), `tout_d` (`MAX_SLOTS × H`)
   with `MAX_SLOTS = 2 × MAX_M = 8` — a "wide" row costs two GEMV rows (§6).
4. SIMD tiers run **two dispatches** over a work-stealing cursor array (`decode_phase`); the scalar
   tier runs the five/six-phase schedule (`forward_phase`). Dispatch 0 = gate+up, dispatch 1 = down;
   the transforms, activation, and the weighted accumulate run inline on whichever worker finishes
   a 128-column

# B70 decode kernels — chapter close-out (E24)

Status: **closed for GEMV/DPAS optimization.** One kernel family selected, one decision escalated, a
repeatable exactness gate in place, and a ranked handoff. This page is the summary of record; `b70-kernels.md`
§2c keeps the item-by-item history (13 → 13x) and `notes/b70/out_dpas.txt` / `out_gemv.txt` hold the raw
measurements.

## Decision record

| # | Decision | State | Basis |
|---|---|---|---|
| D1 | **Rev J (transposed tiles) is the decode kernel** for K = 2–16 | **adopted, pending D3** | 1.27–1.46× over rev I, 2.5–3.1× over rev G at every measured point; bit-exact; `out_dpas.txt` |
| D2 | **Combine stays a separate launch.** Do not fuse it into the producer with atomics | **adopted (refuted the alternative)** | fused costs +6.4…+8.4 µs gate / +13.6…+15.8 µs down; the atomic protocol alone is ~8.7 µs against 1.9 µs of saved round trip (13w) |
| D3 | **Accept the intra-tile permuted device layout** (`dword q·K+i → i·8+q`, produced when weights are staged into VRAM) | **ACCEPTED (owner decision), and now priced** | It is what buys D1's win: same bytes, same capacity, same DRAM traffic, bit-identical outputs, but the VRAM tensor is no longer byte-identical to the checkpoint. Measured (`probe_permute`, `out_permute.txt`): a device permute of the whole 512 MiB resident set costs **3.46 ms** at K=3 (4.24 ms at K=6) against 1.19 ms for a straight device copy — i.e. **+5.4 % on a load that already takes ~64 ms** over the measured 8.37 GB/s link. Doing it on the parent instead is worse: a host permute-copy runs at **6.8 GiB/s (K=3) to 9.1 GiB/s (K=6)** against memcpy's 20.4 GiB/s, and the link itself is ~7.8 GiB/s, so for K=3 staging becomes permute-bound (+~20 %) while also burning parent cores that §6 prices as scarce. **Recommendation adopted: ordinary DMA staging + a device-side permute at admit.** One caveat on "pay it once": that is true only for experts that never leave VRAM — a readmit after eviction pays it again, 226 µs per 14 MiB admission (+13 % of that admission's transfer). §4a's cache tier therefore permutes **on admit**, not once per process |
| D3-alt | **One staged in-RAM layout, consumed verbatim by the B70**, with the CUDA path still unpacking to native from that different base | **demonstrated end-to-end on AVX2** (planar dwords + group-2 banding, 16/16 bit-exact with negative controls, banding rate-neutral); remaining work is the layout marker in the handoff and keeping D3 for non-planar tiers | The production AVX2 repack (`_copy_repacked`, planar) already emits exactly rev J's dword order — byte-identical over 1.536 M dwords — and rev J reads the full staged form bit-exactly at the same rate (−1.3…+2.0 % planar; −4.6…+1.0 % banded) (`out_cpu_layout.txt`, `gate_dpas.py --staged`). D3's device permute survives as the fallback for tiers where staging is not planar (AVX-512 group 8; non-integer rates group 0), which is what makes the marker mandatory rather than cosmetic |
| D8 | **Fuse gate+up into one launch at KS=1 when the separate launches under-fill the device**; keep launches separate otherwise | **adopted (measured), and tested off E=10** | Fused gate+up beats the best unfused schedule at every row count (x1.04 at rows=1, x1.13 at 8, x1.17 at 16), bit-exact, and halves the gemm launches in the layer. The condition is occupancy, not taste: fusion and split-K both buy parallelism, so the fused kernel wants KS=1 (`out_e25_fuse.txt`). **Grid sweep at E=10/32/96 (`out_egrid.txt`)**: the rule predicted correctly in 15 of 18 cells, and all three misses are fusion winning by 3-6% where the rule said "separate" — i.e. the 0.6·HW_THREADS cutoff marks *where the benefit disappears*, not where fusion starts to hurt. Read it that way: below the cutoff fuse (1.35-1.63x); above it the choice is a wash within ±6%, so prefer fewer launches**. **Joint form, from E=2/E=4 (`out_low_e_grid.txt`):** fusion and split-K are two purchases of the same thing, so pick them together — the optimum at every E measured lands with the gemm grid at ~0.6–0.8 × HW_THREADS (E=2 fused KS=4 → 1280; E=4 fused KS=2 → 1280; E=10 fused KS=1 → 1600; E=96 needs neither). At E=2 the best schedule is fused *and* KS=4 (9.7 µs vs 17.6 fused KS=1, 14.1 separate KS=4), so the E25a phrasing "they are substitutes, fuse at KS=1" was an E=10 artifact. **Second condition, added after measuring the E=32 result below: fusion also has a cache cost** — a fused launch holds both projections' streams at once, so it loses its advantage once `2·E·bytes > L2` while a single stream still fits. Prefer fusing where the fill test passes, and treat the L2 condition as a flag rather than a veto. **Qualification added by the bit-rate sweep (`out_fusion_penalty_k.txt`): bytes locate the band to within ~1.5× and predict its DEPTH trend (worst-case penalty 1.16× at K=2, 1.27× at K=3, 1.88× at K=6), but not its sign at the edges** — K=2 at E=32 sits inside the band and fusion still won by 1.32×, and K=3 at E=16 flips sign between KS=1 and KS=2 at identical bytes. So `best_launch()` decides from the measured tables and treats the byte test as a warning (it excludes fused candidates only when the caller opts in with `enforce_cache_rule`); the fill test stays the operative one, and `~tie` marks cells inside the noise floor. **Wired in (`layer_us_joint()`)**: `plan_operating_point.py` and `plan_concurrency.py` now price the layer from the joint (fused?, KS) table instead of calling the fill-only `should_fuse()` + `layer_us_fused()` pair, and degrade to the older per-projection tables wherever the joint grid has no cell (E beyond the measured ladder; rows 2/4 were a hole until `out_rows_2_4.txt` filled them, and their absence had been silently disabling the rule in the operating-point grid) rather than borrowing a neighbouring row count |
| D9 | **One combine launch for the fused gate+up pair, with one work-item producing both projections** (grid = output count, not 2×) | **adopted (measured)** | Beats the two-launch form at rows=8 (−1.1 µs) and ties at 1/16, so the layer loses a launch without losing time; the naive merge (one launch, 2× grid) *lost* by 1.9–3.8 µs, and four explanations (dirty L2, timing protocol, runtime-`KS` address folding, non-contiguous partial allocations) were tested and refuted before grid shape was isolated by per-stage attribution. ## The number that ends the optimization chase

At rows=1, gate_proj: **14.0 µs = 437 GB/s effective** against a measured 484 GB/s stream slope and 674 GB/s
copy peak. **~90 % of achievable**, i.e. the streaming path is at the wall. **Asterisk added later, and it
matters:** that case has E=10 and 5.9 MiB of weights, which fits the device's 24 MiB L2 (`devinfo`), and the
timing loop re-reads the same tensors — so 437 GB/s is partly L2 bandwidth, not DRAM. The DRAM-regime figures are
the large-E cases: E=96 fused achieves 492 GB/s at rows=1 and 287–292 GB/s at rows=16 (`out_egrid.txt`), and the
quantization ladder makes the point sharply — at E=10, 3× the bytes changes the time by 3% and reports up to
693 GB/s, which exceeds the 674 GB/s copy peak and so cannot be DRAM (`out_quant_ladder.txt`). Rule for reading
any rate here: check the working-set size against L2. Its own floor mode says the kernel
is balanced rather than dominated (`NO_MAD` 12.5 > `FETCH_ONLY` 8.9 and > `ALU_ONLY` 10.9; components sum to
21.3 vs 14.0 — ~35 % overlap). Unpack instruction count is no longer the lever.

What is left, in measured order of size:

1. **Fixed cost per projection ≈ 7.8 µs (gate) / 8.4 µs (down)** — ~24 µs of a 43.6 µs b=1 layer is launches,
   per-thread setup and the combine kernel. Attack: gate+up in one launch (E25), one combine per *layer*
   instead of per projection, cheaper per-thread setup.
2. **Bytes and locality**, now that streaming is at the wall: placement, ordering, the 18.35 GiB threshold.
3. **Routing**, if D3 is declined: it is this device's recurring tax, measured three ways — rev H's `iselect`
   cascade (+86 % when doubled), rev I's gathers (~2× better still), rev C's operand re-packing (48 % of its
   loop). Rev J escapes it because the *layout* removes it, which is the real argument for D3.

## Refuted along the way — do not re-attempt without new evidence

- "Decode is bandwidth-bound" as a design premise (true of the model from day one, true of the machine only at
  rev J); and its successor "decode is instruction-bound", true of every kernel through rev H.
- Materializing/expanded-byte operand layouts at load time (rev D), dense contiguous stores (confounded, never
  cleanly tested — item 13i), deeper trellis prefetch (null on revs F/H/I/J), in-register B via `apply`
  (`DPAS_REG=1`, bit-exact and much slower), sub-group barriers on transposed geometry (hurt),
  `NTOK < 16` single-row DPAS (rejected by the backend: minimum accumulator area), and a standalone
  legal-shape oracle for `joint_matrix` (it rejected a shape rev G runs daily — LESSONS 40).
- Loading optimizations as a rescue for the dp4a path (this page's D5; the trade is a wash by measurement).

# MoE CPU offload: tuning knobs, and what each one does to the data

Three families matter:

* **A. Structural knobs** change the *shape* of the shared-memory region and of every payload in
  flight (`SLOTS`, `SLOT_ROWS`, `WSLOT_MB`, `BATCH_EXPERTS`, …). A port has to reproduce these
  shapes exactly on both sides of the boundary.
* **B. Policy knobs** change *which* path a given layer/step/expert takes, without changing any
  shape (`STREAM_T`, `MIN_ROWS`, `STREAM_FUSED_T`, placement knobs).
* **C. Implementation knobs** change only *how* a hop is executed (`MEMOPS`, `PIN`, `SPREAD`,
  `MAX_ISA`, `SWIZZLE`, `STAGE_THREADS`).

Sources: `MoeCpuTuning` (`exllamav3/model/moe_cpu_host.py:84-177`, the single place env vars are
read), `BlockSparseMLP_CPU` (`exllamav3/modules/block_sparse_mlp_cpu.py`),
`exllamav3/exllamav3_ext/cpu/moe_handoff.h`, `exllamav3/util/backend.py:49-51`, and
`doc/env_vars.md` (362-822). Measured effects are from `measured-costs.md` §5, §7, §8.

Anything in `MoeCpuTuning` can also be set without env vars by mutating the module-level `TUNING`
singleton before constructing the model — that is the intended way to sweep in one process.

---

## 1. Mode selection (these decide the set of paths that exist at all)

| knob | effect |
|---|---|
| `-mcl N` / `EXL3_MOE_CPU_OFFLOAD` | first N eligible MoE layers route **all** their experts to the worker. `cpu_offload=True`: routing output is the worker's sum, no expert-range masking. Decode uses P1' (copy path, `kind=COMPUTE`, unconditional readback); prefill uses P2/P3. |
| `-mcs K` / `EXL3_MOE_CPU_SPLIT` | every eligible layer keeps experts `[0, E-K)` on the GPU and `[E-K, E)` in the worker. Shrinks the module (`num_local_experts`, `routing_first/last`), so the GPU-side fused/reconstruct tiers see a smaller expert range and out-of-range picks are masked in-kernel. Decode uses P1 (`kind=COMPUTE_GATED`). Capped at `E-1` with a notice. |
| `EXL3_MOE_CPU_SPLIT_LAYERS` | limit the split to the first N layers (default 0 = all eligible). |
| `-mcpa` / `EXL3_MOE_PINNED_ARENA` | worker arena = shared memfd/section mapped **and page-locked by the parent**, each expert laid out as one contiguous `gate, up, down` block. Two consequences: streamed prefill DMAs from the arena on the copy stream (no stage job, no stager memcpy: +32% prefill measured) and promote-on-miss becomes possible. Costs ~0.2 s/GiB of registration at load and double-counted RSS. |
| `EXL3_MOE_ARENA_HUGE` (`2m` or `1g`) | back the arena chunks with hugetlbfs pages instead of shmem (needs `vm.nr_hugepages` reservations). |
| `EXL3_MOE_ARENA_HUGEPAGE` | THP promotion: post-load `MADV_COLLAPSE` pass on Linux (background thread), `MEM_LARGE_PAGES` per chunk on Windows. Affects CPU-side GEMV page-walk cost only, not any shape. |
| `EXL3_MOE_CPU_LOAD_BATCH` (32) | experts the worker reads per deferred load pass; bounds transient host memory above the arena to a slice of a layer. **No effect on arena layout or contents.** |
| `EXL3_HOST_MEM_RESERVE_MB` | guard applied before arena chunks (and the n-gram table). |
| `EXL3_MOE_CPU_START_TIMEOUT` | how long the parent waits for the worker's `ready` flag after the last layer is handed over. |

Eligibility for both modes (checked on header metadata only, `cpu_maybe_*_load`): CUDA device,
layer-split mode (no TP), mul1 codebook, tile width ⇒ `K ∈ 1..8` or `1.5/2.5/3.5`, activation
silu/gelu/swiglu_oai (gated) or relu2 (gateless), and biases either all-or-none per projection.
`MoeCpuHost.ensure_started` additionally requires **uniform `hi`, `ho` and `topk` across all
registered layers** (assert), because the slot sections must stay contiguous 2-D blocks.

## 2. The compute handoff region (shape family A)

| knob | default | what it changes |
|---|---|---|
| `EXL3_MOE_CPU_SLOTS` | 4 (max 8 = `MOE_MAX_SLOTS`) | number of compute slots ⇒ job-ring depth in flight ⇒ how many `cap_rows` chunks the parent can have issued+un-collected at once. The multi-chunk issue loop inline-collects the oldest job once `len(jobs) == num_slots`, so slots directly set the D2H/H2D pipelining depth; at 1 the prefill path degenerates to lockstep. Pinned cost `slots × slot_size`. |
| `EXL3_MOE_CPU_SLOT_ROWS` (`cap_rows`) | 64 | rows per job ⇒ `x` = `cap_rows × hi × 2 B`, `out` = `cap_rows × ho × 4 B`, `sel`/`w` = `cap_rows × topk × (4,2) B`; a prefill of `rows` becomes `ceil(rows/cap_rows)` jobs. **Also a functional gate:** the fused decode path (P1) refuses jobs with `rows > cap_rows` and silently falls back to the copy path, so `cap_rows < 32` forfeits the fused path for speculative-verify batches (`TEMP_ROWS_GRAPH = 32`). Measured: 32 gives 105 tok/s vs 93 at 64 (smaller chunks pipeline better against the GPU); 128 + 8 slots gives 97. |
| `EXL3_MOE_CPU_THREADS`, `-mct` | phys cores − `HOST_CORES` | pool size for the GEMV phases. Bandwidth-bound past ~8 here (45 GB/s wall at 8-16 threads); `-mct 8` measured 98 tok/s vs 93 at 15, i.e. free. |
| `EXL3_MOE_HOST_CORES` | 1 | cores withheld from the pool; the parent is then *confined* to them. The one host core matters because the parent's forward thread and CUDA driver threads otherwise preempt a pinned worker at its per-dispatch barriers (docs: 11-32 vs 30-36 tok/s on a 12-core box). |
| `EXL3_MOE_CPU_PIN` / `EXL3_MOE_CPU_SPREAD` | 1 / 0 | pin one worker thread per physical core (SMT siblings last) / order cores round-robin across L3 domains first. Pure scheduling. |
| `EXL3_MOE_MEMOPS` | 1 | stream memory operations vs the spin-wait kernels for every flag write/wait. Measured: 1.8 µs vs 2.9 µs host enqueue, 6.4 vs 10.7 µs round trip, and decode 91.7 vs 93.2 tok/s (noise). The kernel path is the only one with a 30 s timeout; with memops, worker death is caught by the host watchdog, which unblocks pending waits by writing satisfying values into the flags. |
| `EXL3_MOE_SPLIT_FUSED` | 1 | **path switch**: `0` makes `cpu_split_submit` skip the fused decode handoff entirely and take the P1' copy path (three `cudaMemcpyAsync`, an `int32` cast and a pad per layer per step). Exists for A/B testing; costs ~6 µs/layer at decode (§4). |
| `EXL3_MOE_POOL_PRIME` | on | worker primes (wakes) the pool at `pass_wake` and before its GPU payload arrives, so the pool is spinning when the job lands. Off ⇒ first dispatch pays futex wake-up. |
| `EXL3_MOE_CPU_SMALL_WORKERS` | 0 (off) | caps participants for jobs with ≤ 2 chunks (`Pool::run(n_run)`), trading per-barrier stragglers against bandwidth. |
| `EXL3_MOE_CPU_MAX_ISA` | auto | caps the CPU kernel tier (`scalar/avx2/bw/vnni/vbmi`). Changes **the packed layout rule** too (capping below `bw` disables band-8 and, on `avx2`, switches to band-2+planar for integer rates), so parent, child and GPU restore must agree — they all query `exl3_moe_cpu_swizzle_group`. Read once per process, parent and child independently: it must be set before either starts. |
| `EXL3_MOE_CPU_WIDE` | 1 | a row whose small elements would all round to zero is carried as two int8 rows ⇒ that chunk uses 2 GEMV rows per token, doubling GEMV work and requiring `MAX_SLOTS = 8`-row scratch. Measured decode 96.1 vs 93.2 tok/s off/on (noise either way on this model, i.e. wide rows are rare here); the microbenchmark difference is proportional to how often rows go wide. |
| `EXL3_MOE_CPU_SWIZZLE` | 1 | pack (band/planar) the arena copies. Changes (a) CPU GEMV throughput, (b) whether the streamed path must run `moe_unswizzle_trellis` and allocate the second VRAM ring (`native_slots`). On this AVX2 host: K=3 decode 89.3 vs 93.2 tok/s unpacked/packed; half-integer rates unaffected (they are native on this tier anyway). |

## 3. The streamed prefill path (policy family B, shape family A)

Entered only when `rows ≥ EXL3_MOE_STREAM_MIN_ROWS` and the layer registered `aux` tensors and
`expert_bytes ≤ wslot_size`.

| knob | default | effect |
|---|---|---|
| `EXL3_MOE_STREAM_MIN_ROWS` | 32 | the **path selector** (`bsz < min_rows` ⇒ P1/P1'). Raising it above your chunk size disables streaming entirely: measured prefill 818 vs 1661 tok/s at 2048 rows. |
| `EXL3_MOE_STREAM_T` | 8, scaled per device to `max(8, 8·√(25/bw_GB/s))` | per-expert assignment count above which the expert's weights are streamed instead of computed on the CPU. This is the single biggest prefill lever (measured 2.1× between on and off). *Doc/code mismatch:* `doc/env_vars.md:411` documents the base as `16`; the code constant is `8` (`moe_cpu_host.py:139`, `TUNING.stream_t`) and the calibration comment says 8 was best on Gen5 links — the log line `pinned->device 13.4 GB/s, stream_t 11` is `8·√(25/13.4)`, confirming 8. |
| `EXL3_MOE_CPU_WSLOTS` | 2 (max 8) | depth of the weight-staging ring (pinned and VRAM) ⇒ how many expert batches can be in flight on the copy stream while the compute stream works the previous ones. 1 makes streaming lockstep with the DMA. |
| `EXL3_MOE_CPU_WSLOT_MB` | 32 | per-slot bytes. Two hard consequences: an expert must fit alone (`expert_bytes ≤ wslot_size`, else the layer never streams), and `per_slot = min(wslot_size // expert_bytes, STREAM_BATCH_EXPERTS, 256)` caps the batch size. Sized for the *largest* layer, so small experts waste slot space (Qwen3.5's 1.125 MiB experts: 28 fit a 32 MiB slot, but the default batch is 24, so ~14% of the ring is unused). |
| `EXL3_MOE_STREAM_BATCH_EXPERTS` | 24, hard max 256 | experts per stage job / DMA / fused launch. Ceiling is `MOE_JOB_MAX_EXPERTS` (the descriptor's `experts[]` array). Bigger batches amortize the ~175 µs fixed cost per stage job and the per-launch overhead, at the price of latency (a batch is the scheduling unit) and of the VRAM ring. Measured neutral (+/- noise) at 24→48 with `WSLOT_MB=96`. |
| `EXL3_MOE_CPU_STAGE_THREADS` | 4 | scratch threads the stager uses for the arena→pinned `memcpy`. Measured **no effect** 1..8 on this host (16.3 GB/s either way) because a single thread already saturates; the code also spawns fresh `std::thread`s per job, so the fixed cost is not thread-count dependent. Docs say it matters for many small experts on a fast link. |
| `EXL3_MOE_STREAM_FUSED_T` | 256 | per-expert row ceiling for the fused `exl3_moe` tier; above it the batched-reconstruct tier, above `recon.max_rows` the per-expert loop. Sets the streamed tier's temp buffers: `concurrency × T × (2·hidden + 2·interm) × 2 B` per device (halved when 512→256). Between 256 and 64 the tier choice moved prefill by ≤5% (§8), so treat it as a VRAM/planning knob rather than a throughput one — unless routing is very skewed. |
| `EXL3_MOE_STREAM_BATCH_RECON` | 1 | batched-reconstruct tier on/off for streamed experts (off ⇒ per-expert reconstruct loop). Measured neutral: with `STREAM_FUSED_T=64` forcing most experts off the fused tier, batched vs per-expert was 1752 vs 1740 tok/s prefill (§8). |
| `EXL3_MOE_MTILE` | 1 | fused-kernel row-tile tiers 16/32/64 (three launches, largest first) — same rule on both the GPU-resident and streamed tiers (`mtile` in `MoeCpuTuning`, used in `_submit_prefill_streamed`). |
| `EXL3_MOE_FUSED_ROWS` (128) / `EXL3_MOE_FUSED_ROWS_WIDE` (256) / `EXL3_MOE_TILE_N` | | the GPU-resident tier's row capacity and tile shape; `fused_rows` also gates whether `expert_count.tolist()` (a per-layer host sync) is needed at all — see §5. |
| `EXL3_MOE_BATCH_RECON` + `EXL3_MOE_RECON_TILES` / `EXL3_MOE_RECON_BATCH` / `EXL3_MOE_RECON_PAD` / `EXL3_MOE_RECON_ROWS` / `EXL3_MOE_RECON_MB` / `EXL3_MOE_RECON_MAX_ROWS` / `EXL3_MOE_RECON_FOLDED` | see `doc/env_vars.md:722-755` | the batched reconstruct tier for GPU-resident experts (`BATCH`: on/off; `TILES`: legacy tile-budget cap; `BATCH`: experts per group; `PAD`: padded-to-real row ratio per group; `ROWS`/`MB`: padded-row and dequant-scratch budgets; `MAX_ROWS`: explicit row cap; `FOLDED`: fold both Hadamards into the dequantized weights). The **same** `BatchReconLayer` object is reused by the streamed tier (`_stream_recon_layer`), so `RECON_MAX_ROWS`/`RECON_ROWS` also decide where a *streamed* expert leaves the batched tier for the per-expert loop, and `RECON_FOLDED` changes its numeric behaviour on both paths. |
| `EXL3_MOE_FUSED_DET` (and `EXL3_MOE_RECON_DET`, which follows it) | 1 | deterministic slot+gather accumulation: allocates `assignments × hidden` fp32 scratch per call (~320 MB per layer call at 4k tokens on Qwen3.8) and one `exl3_moe_gather` (measured 135 µs/layer at 2048 rows). Cost is VRAM, not time — but it *is* a large prefill-time allocation the autosplit planner must budget. `RECON_DET` only matters where the batched tier cannot write into the slot scratch (the streamed tier, or `FUSED_DET=0`). |

## 4. Placement (which experts are CPU-resident)

| knob | default | effect |
|---|---|---|
| `EXL3_MOE_CPU_SWAP=0` | dynamic on | static tail (no placement changes after load) vs periodic sweep every `EXL3_MOE_CPU_SWAP_INTERVAL` (128) decode steps, run from the generator's queue-drained hook; `SWAP_HYST` (2.0) and `SWAP_FLOOR` (8.0 × mean count) gate swaps; `SWAP_MAX` (64) caps swaps per sweep round. A swap re-reads the promoted expert **from the checkpoint** into the demoted expert's GPU slot in place (pointers stay valid) and quiesces the device (`torch.cuda.synchronize`) — a stop-the-world event measured at **≈6 ms per sweep**, which is why it is deferred to between generations (`measured-costs.md` §8.2). |
| `EXL3_MOE_CPU_PROMOTE` (4) + `-mcpa` | promote-on-miss | replaces the sweep: each decode step, experts the worker computed are DMA'd into spare GPU slots on a side stream (`_PROMOTE_BUDGET = 6` layers/step, `_PROMOTE_RATIO = 1.5`, `_PROMOTE_DECAY = 0.98`/step), and the least-used resident goes back into the freed worker slot. No checkpoint read, no quiesce. The hook costs **~2-3 ms of host time per decode step** (`measured-costs.md` §8.2), and the mode does not exploit a saved profile: controlling the placement start gives 78.7 cold / 77.7 warm for `-mcpa` against 78.0 / 100.7 for plain `-mcs 192` (§8.3). |
| `EXL3_MOE_CPU_SPLIT_STATS` (explicit profile), `~/.cache/exllamav3/expert_stats/<hash>.json` | | permutes experts hot-to-cold at load from a saved profile (`_STATS_SAVE_INTERVAL = 4096` steps, `_STATS_MIN_STEPS = 64`), so the GPU slice starts with the frequent experts. The permutation is applied to the router weights too (`cpu_post_load`). **Measured effect: 5.87 → 4.42 CPU-computed picks per token and +12-22% decode** (`measured-costs.md` §8.3). The cache key is model dir + expert count only, so it is shared across split sizes and placement modes and is rewritten at every unload: benchmarks must delete it, pin it with `EXL3_MOE_CPU_SPLIT_STATS`, or redirect `block_sparse_mlp_cpu.EXPERT_STATS_DIR` (what the test suite does) or they are measuring each other. |
| `EXL3_MOE_CPU_SWAP_DEBUG`, `…_VERIFY`, `EXL3_MOE_CPU_PROMOTE_VERIFY` | off | counters / readback comparison against the checkpoint (very slow). |

# B70 offload: architecture

Anchors are to this tree (`dev`, v1.6.5 + the `doc/prep` commits). Costs marked **[M]** are measured
on this box (see [`notes/b70/README.md`](../../notes/b70/README.md) for the raw logs); **[P]** are
projected from hardware figures and must be re-measured before they are quoted anywhere else.

---

## 1. The one structural decision: the B70 is a *worker*, not a *device*

Everything the model itself runs (attention, dense MLP, router, shared expert, sampling, KV cache)
stays on the CUDA device, in torch, unchanged. The B70 takes the role that `moe_cpu_host.py`'s child
process plays today: **it consumes jobs from the shared-memory ring and fills the slot's output**.
It is reached through a Level Zero / SYCL engine, not through torch (there is no `torch.xpu` in this
venv, and even with one there is no reason to make the model's forward aware of a second vendor).

Why that framing rather than "make the B70 a second compute device the model loads experts onto":

* The parent side of the protocol is then *literally unchanged*: the fused decode handoff, the four
  flags per slot, the `COMPUTE_GATED` empty-job trick, the `consumed` gating, the ring geometry, the
  watchdog, the deferred collect, and every Level-D invariant in `doc/prep/port-acceptance.md` keep
  holding because nobody on the CUDA side knows who did the arithmetic. Measured proof that this is
  possible: `probe_cross.py` A1/A2/A3 **[M]** — one page-locked region is written by a B70 kernel and
  read by the 3090, a `cuStreamWriteValue32` from the 3090 is visible to a B70 kernel, and a flag
  written by a B70 kernel retires a `cuStreamWaitValue32`.
* The five capabilities `doc/prep/moe-cpu-offload-data-paths.md` §9 lists as "what a port needs from
  the accelerator" map onto this box as:

| requirement | CUDA today | B70 engine | status |
|---|---|---|---|
| page-locked host memory with a device mapping | `cudaHostRegister(PORTABLE\|MAPPED)` + `cudaHostGetDevicePointer` | `register_host_memory(ptr, len, ctx)` on the region the parent already registered | **[M]** works; the region must be pinned by CUDA, *not* by the xe driver (`cudaHostRegister` on `sycl::malloc_host` fails `invalid argument`) |
| kernels that store to / load from it, system-scope ordered | `int4` stores, `__threadfence_system()`, `ldg_acquire_sys` | plain volatile stores + `sycl::atomic_fence(acq_rel, system)` | **[M]** works for stores (100/100 reps, cold and host-dirtied lines, in-process and cross-process); **loads are latency-bound (~65 ns each)**, so the payload comes in by DMA; a `sycl::atomic_ref` at *any* scope on a registered foreign pointer loses the device (`UR_RESULT_ERROR_DEVICE_LOST`) — publish flags with a fenced volatile store (`LESSONS` 4) |
| stream-ordered flag wait/write without SM occupancy | `cuStreamWaitValue32` / `cuStreamWriteValue32` | not needed on the B70 side: it *produces* flags (kernel store) and *consumes* them by spinning host-side, exactly as the CPU worker does | no Level Zero equivalent exists (checked `ze_api.h` 1.18: only events/timestamps); not required |
| multiple streams + events, contiguous async copies | compute + copy streams, `wready_ev`/`wconsumed_ev` | one in-order queue for jobs + one for weight transfer; `sycl::event` for the engine thread only (**never** on the parent's path) | **[M]** `.wait()` costs 24 µs, so event waits belong to the engine thread's idle path, not the per-job path |
| the GPU-side expert kernels | `exl3_moe*`, `reconstruct*`, `hgemm*`, `moe_unswizzle_trellis` | unchanged on the 3090; a *new* implementation for the B70 (see `b70-kernels.md`) | this is the port |

*Consequence for the plan*: no change to `BlockSparseMLP.forward`'s structure, no new torch device,
no TP interaction, and the CPU worker stays available both as a fallback and as the **numerical
oracle** for the new kernels.

---

## 2. Where the bytes live

### 2.1 Four disjoint homes, three computers

**An expert has exactly one home, and its home does its arithmetic.** No replication between the
3090 and the B70:

```
   S_g   home = 3090 VRAM      936 GB/s peak   quota: COMPUTED, see 2.1a (16.6 GiB on Qwen3.8/GLM at
                                               4k ctx, not the 2 GiB an earlier draft assumed)
   S_b   home = B70 VRAM       ~608 GB/s peak <- the new tier, filled to capacity
   S_c   home = host DRAM      ~45 GB/s CPU   the arena; also the source for a 655 us upload to S_b
   S_d   home = NVMe           ~5.0 GB/s [M]  read through a bounded pinned ring when needed
```

#### 2.1a Pricing the parent's other work: two bills, not one

The 3090 is also running attention, the linear-attention states, the shared expert, the router and the
sampler, so `S_g`'s quota cannot be assumed. `plan_parent_budget.py` splits that into the two things
"the 3090 is busy" actually means, because they pull in opposite directions (**[M]**, byte bills from
the shard headers; `out_parent_budget.txt`):

**CAPACITY bill — what must be resident.** Both reference models are hybrid linear-attention with
compressed KV (Qwen3.8: 36 of 48 layers linear, 12 full at 2 KV heads → 24 KiB/token, 108 MiB state per
*sequence*; GLM: 34 of 45 linear, 11 MLA-sparse with `kv_lora_rank` 512 → 22 KiB/token, 136 MiB state),
and the tables that look terrifying are not resident at all: Qwen3.8 carries **49.91 GiB of per-layer
n-gram embeddings** plus embed/lm_head, which `modules/row_table.py` row-gathers from host/disk
(`ngram_gather_cpu`) — capacity on disk, a few rows per token in traffic. What must actually sit in the
24 GiB is 4.05 GiB (Qwen3.8) / 5.67 GiB (GLM) of streamed non-expert weights, plus KV/state, plus
reserve → **~16.6 GiB free for experts at 4k ctx, b=1**, i.e. 265 of 512 slots per layer on Qwen3.8 and
42 of 288 on GLM. The 2 GiB this plan previously assumed was a guess, and it was 8× too stingy:

| `S_g` | Qwen3.8 `h` | CPU ms/token | GLM `h` | CPU ms/token |
|---|---|---|---|---|
| 2 GiB (old assumption) | 97.6 % | 0.42 | 70.8 % | 19.6 |
| 8 GiB | 99.6 % | 0.07 | 75.5 % | 16.4 |
| **16.6 GiB (computed)** | **100.0 %** | **0.00** | **81.1 %** | **12.6** |

That single correction moves GLM's hit rate by 10 points and its CPU residue by 35 % — more than any
hot/cold ordering choice does — and it makes Qwen3.8 fully homed with ~12 GiB of *surplus* capacity,
which reopens replication as an option (below).

**TRAFFIC bill — what competes for bandwidth.** A decode token on Qwen3.8 streams 86.4 MiB/layer of
non-expert weights = **96.8 µs of the ~250 µs parent window**, i.e. the parent runs at ~39 % of its own
peak bandwidth at b=1. So the 3090 is *latency-bound, not bandwidth-bound*, at small batch: expert reads
there are cheap in bytes/second terms and the 3090 remains the faster expert home even while busy
(~576 GB/s nominally spare versus the B70's measured 292). Nobody has measured that spare, because the
estimate assumes perfect overlap — E18 does.

**So what does the parent's other work do to placement?** It changes the objective, not the ordering.
Costs on `S_g` are *serial* with the parent's own stream; `S_b` and `S_c` run concurrently. The right
objective is therefore the per-layer maximum, not the sum the earlier draft minimised:

```
wall/layer = max( T_parent + picked_bytes(S_g)/936 ,  picked_bytes(S_b)/rate_b ,  picked_bytes(S_c)/47.4 )
```

and this is where the "distribute the hot experts across both accelerators, still disjoint" idea lands.
`plan_parent_budget.py` evaluates it as an LPT greedy (walk the hot list once, give each expert to the
home whose resulting term is smallest) against the frequency-ordered cut (`P_order`, the plan's rule):

| model | rows | `S_g` slots | `P_order` µs/layer | `P_lpt` µs/layer | winner |
|---|---|---|---|---|---|
| Qwen3.8 | 1 | 30 | 253 | 253 | tie (parent-bound) |
| Qwen3.8 | 8 | 30 | 314 | **278** | fair split, +13 % |
| Qwen3.8 | 8 | 120 | 304 | **299** | fair split, +2 % |
| GLM | 1 | 30 | **571** | 623 | ordered, +9 % |
| GLM | 4 | 120 | **695** | 865 | ordered, +20 % |

Which is a genuinely mixed answer, and the reason is visible in the objective: **fair-splitting wins
when the B70 is the binding worker** (Qwen3.8 at b≥4, where the 3090's spare rate beats it) and **loses
when the CPU is binding** (every GLM row above, where `S_c` still carries 19–30 % of picks): spreading
hot experts over both VRAM homes necessarily leaves *colder* experts to the CPU, and the CPU term is
`bytes/47.4` — the most expensive byte on the box. So the rule is not "hottest on the 3090" and not
"parity"; it is *minimise the maximum term*, which under a CPU residue means pack the fast homes with
the hottest first, and once the residue is gone (Qwen3.8 with the computed slice: `h` = 100 %) means
balance the two VRAM homes by load, which is what `P_lpt` does.

The measured rate ratio also kills the original argument against replication. §2.1 said the homes'
read rates were "within 1.5×" — that was spec-to-spec (936/608); footprint-matched they are 3.2×
apart on Qwen3.8 and 7× on GLM. Disjointness still holds for GLM (no spare capacity to duplicate
with), but Qwen3.8's ~12 GiB surplus makes a *third* option real: replicate the hottest few experts on
both cards and steer each pick to the idle home, which decouples placement from load-balancing entirely
at the cost of capacity. It is not adopted here — E14 measures whether the surplus survives real
context lengths, and E20 would be the gate for the steering logic.

**Does any of this hold for the bigger recipes?** Yes, and it was checked rather than assumed
(**[M]** `plan_quant_scaling.py`, `out_quant_scaling.txt`; the K = 4/5/6 tile rates are newly measured
in `out_rates_footprint_hiq.txt`, not extrapolated). Five Qwen3.8 checkpoints, `S_g` computed per
recipe, 4k ctx, b=1:

| bpw | expert MiB | slots/layer | `h` / live | CPU ms/tok | dev MiB/layer | matched GB/s | µs/layer | b=8 winner |
|---|---|---|---|---|---|---|---|---|
| 2.05 | 1.215 | 335 | 100 % / 356 | 0.00 | 12.1 | 292 | **44** | fair split (+7 %) |
| 2.68 | 1.563 | 249 | 100 % / 512 | 0.00 | 15.6 | 292 | **56** | fair split (+4 %) |
| 4.05 | 2.411 | 162 | 94.8 % / 512 | 1.34 | 22.9 | 294 | **81** | fair split (+3 %) |
| 5.05 | 3.009 | 127 | 100 % / 258 | 0.00 | 30.1 | 290 | **109** | fair split (+9 %) |
| 6.05 | 3.608 | 104 | 90.4 % / 500 | 3.68 | 32.6 | 243 | **141** | **hottest-first (+43 %)** |

* What scales is `expert_bytes` (2.4× from 2.68 → 6.05), so a decode layer's footprint grows from 12 to
  33 MiB, the resident *count* per layer falls 512 → 104, and the µs/layer rise is mostly just more bytes
  at a rate that barely moves (243–294 GB/s across every K). Offload still hides at b=1 for all five
  recipes (44–141 µs inside a ~250 µs window).
* What does **not** scale is the parent's byte bill: 69–101 MiB/layer, 31–45 % bandwidth duty, across all
  five recipes — because the quantisation recipe holds the streamed non-expert tensors near a fixed width
  instead of scaling them with the experts. §2.1a's "the 3090 is latency-bound with spare bandwidth" is
  therefore recipe-general on this model, and my initial guess that duty would reach ~83 % at 6.05 bpw
  was wrong by ~2×.
* The policy rule predicts its own crossover across the whole range: fair-split wins wherever the residue
  is zero or dust-small, and at 6.05 bpw — the one recipe where a real 9.6 % of picks land on the CPU —
  hottest-first wins by 43 %. `EXL3_MOE_B70_BALANCE=auto` selecting on `h` is exactly this boundary, so
  the same knob covers every recipe, with one condition: `h` must be read against the **live** expert
  count (the `512L` / `258L` column), since the decayed profiles' dust tail otherwise reports 100 %
  residency for recipes that are only ~90 % homed.
* One rate caveat, kept because it is a live E4c lead: fatter tiles make banding slightly *positive* —
  1.06–1.07× at K = 5/6 and 64–128 MiB, versus 0.96–1.05× at K = 2.5/3.0. Still not consistent in sign
  across footprints, so §2.2's decision stands, but "repacking buys nothing" was measured on thin tiles
  and the trend runs the other way as bits rise.


Disjointness is the default, not an oversimplification: with a CPU residue to serve, every GiB
duplicated is a GiB that cannot hold a *different* expert, and on an oversized model that GiB is the
difference between the CPU computing a pick in 199 µs and a device computing it in 31 µs. (The earlier
justification — that the two devices read at within 1.5× — was spec-to-spec and does not survive
measurement; see 2.1a.) Placement is therefore a **partition problem over three (or four) homes**,
sized by each
home's byte budget, and — for `S_g` — by the existing autosplit weight-versus-KV trade
(`exllamav3/model/model_ls.py`, per-module `autosplit_prepare`/`autosplit_extra_measure`) now
evaluated with the B70 as the alternative home for experts rather than the disk.

Two things follow, and both are costs, not freebies:

* **A row whose picks live in more than one home is computed in pieces** — one job per home holding
  ≥1 of its picks, each writing its own partial, combined by the parent in a fixed order (3090
  in place, then the B70 slot, then the CPU slot: the `cpu_split_combine` add already does this, and
  no atomics are involved, so determinism is preserved). The penalty is a duplicated activation
  payload and an extra handshake on that row, not a correctness hazard. `σ`, the *spanning fraction*,
  becomes a first-class placement metric (§4a, gate E13) and the placement may be re-ordered to
  reduce it.
* **The CPU is a compute tier, not a spill yard.** It wins whenever the bytes would have to move
  further than the arithmetic: copying an expert into a device costs `bytes/link` (655 µs for GLM's
  9 MiB) *before* the first useful byte is read, while computing it where it already lies costs
  `bytes/45 GB/s` per use and never moves anything. The rule that falls out of that (§4a) is a
  ~3-4 use break-even, and it is roughly model-independent.

`S_d` is reached by models whose expert set exceeds host DRAM as well as both cards —
[`§4a`](#4a-models-that-exceed-the-tiers-hit-rate-engineering) is about that regime, and about the
one before it (both VRAM tiers full, `S_c` comfortable), which is where
GLM-5.3-Flash@3.05 bpw (108.84 GiB of routed-expert trellis, present on this box) actually lives.

Because the homes are contiguous ranges of one permutation, the mechanism is the existing one with a
second cut point: the profile sorts experts hot-to-cold (`cpu_post_load` permutes the router weights
to match), `[0, F_g)` is the 3090's `num_local_experts` slice, `[F_g, F_g+F_b)` is the B70's, and
`[F_g+F_b, E)` stays with the CPU — which is exactly `moe_split_map_kernel`'s translate
(`routing.cu:1114-1122`, `p >= first_cpu ? p - first_cpu : -1`) generalised from a threshold to a
range, per home. Three homes, two cut points, no new addressing machinery.

Loading: the engine child receives the same `("layer", spec)` pipe messages as the CPU child, reads
**only the experts whose home is `S_b`** (the cut points are decided before either side loads, so the
3090's slice and the CPU's slice are simply never sent to it), and uploads them over the link
(`14.4 GB/s` **[M]** ⇒ a full 31.9 GiB tier in 2.3 s, overlapped with the parent's own module load —
same trick `model.py:614` uses to hide the CPU child's interpreter start). Aux tensors (`suh`, `svh`,
bias) are uploaded alongside, per expert, in a side table the kernels can index. The parent's
`num_local_experts` shrink (`cpu_maybe_split_load`, `block_sparse_mlp_cpu.py:428`) keeps covering the
3090's slice exactly as `-mcs` does today, so nothing else about the load path forks.

`S_c` handling: **keep the existing host arena byte-for-byte as it is**, including the CPU tier's
packed layout, because the arena is the CPU's *home* copy and at the same time the source for a
migration into `S_b` (655 µs) and for the streamed-prefill path of P3. The B70's VRAM copy is made in
the B70's own layout (below) at upload time; when an expert is migrated into `S_b` later, the bytes
come from the arena in the CPU's layout and are repacked on the way in — a load-time cost paid once
per migration, on the low-priority queue, never inside a job. `EXL3_MOE_B70_ARENA_CAP_GB` bounds the
arena to the `S_c` slice; anything below it is `S_d` (§4a).

When `bytes(S_b ∪ S_g) = bytes(experts)` — nothing in `S_c` — the host arena can be dropped entirely
(`EXL3_MOE_B70_ARENA=0`), a second, independent saving of the same tens of GiB in *host RAM* (which
matters because the arena competes with the page cache the checkpoint reads go through). Opt-in only:
it also means eviction from `S_b` has nowhere to go, so the tier is then a static partition.

### 2.2 Weight layout on the B70

**Decided: the B70 stores experts in native tile order** (**[M]** `notes/b70/probe_rates.cpp`,
`out_rates.txt`, `out_rates_repeat.txt`, `out_rates_footprint.txt`). Banded repacking (the GPU
analogue of the CPU's band-8, k-major along `n`) was measured against native on two geometries across
six working-set sizes: **0.96–1.05×, with no consistent sign** — it helped twice on GLM's wide
`tiles_n` and hurt there elsewhere, and sat on 1.00 for Qwen3.8. That is not nothing, but it is not a
lever either, and it is paid for twice: a repack pass at load, and losing the byte-identity that lets
an expert move between the 3090 and the B70 without translation (§5). So there is no repack at load,
no un-swizzle interaction, and the bytes stay interchangeable with the 3090's kernels.
`exl3_b70_tile_layout(K)` still exists as the single place the layout is *reported* (Gate B4's rule
that no second table may appear), but its answer is `native` for every K, and reversing that needs a
consistent win in the real GEMV (E4), not an analogy to the CPU tiers. One qualifier added by the
higher-quant sweep: banding is not flat in K — at K = 5/6 tiles it measures 1.06–1.07× at 64–128 MiB
against 0.96–1.05× at K = 2.5/3.0 (`out_rates_footprint_hiq.txt`). The sign is still inconsistent across
footprints so the decision stands, but the null was established on thin tiles and the mechanism
(per-item contiguity) should strengthen as tiles fatten — so E4c must run at the deployment's actual K.

The size of the intervention is why the null deserves belief. Banding rewrites the tile index from
native `kt·tiles_n + nt` to `(nt/8)·tiles_k + kt`, cutting the k-step of a GEMV fragment from
`tiles_n × tile_bytes` = 3200 B (Qwen3.8) or 12288 B (GLM) to `8 × tile_bytes` = 640–768 B: an item's
64 tile reads collapse from a 25–60 KiB scatter into one contiguous ~5 KiB run — a 5–16× stride
reduction, and both mappings were checked to be exact covers of the same tiles before timing. What
does *not* come out of the data is a mechanism story: per-item locality ought to matter only when few
streams are in flight, yet GLM's banded gain appears at 2 GiB, 512 MiB and 64 MiB and not at 1 GiB,
256 MiB or 128 MiB. The honest summary is **no reliable gain, and this instrument is not sharp enough
to prove the gain is exactly zero** — the configuration variance (which moves absolute rates ~2×, see
`out_rates_footprint.txt`) exceeds the effect. §12 therefore records the layout decision as made on
engineering grounds and revisitable, not as closed by measurement. One distinction added by
`llm-scaler`: their formats are *repacked* as an interleaved nibble plane plus a plain high-bit plane and
per-32 fp16 scales, so the inner loop is wide and mask-free (b70-kernels.md §2b item 7). That is
repacking for **dequant ergonomics**, which §2.2 never tested — the null above covers locality-driven
repacking only, and an instruction-count-driven repack of the trellis would have to be judged against the
cost of losing byte-identity with the 3090 kernels all over again.

# Acceptance criteria for a port of the MoE CPU offload

What "done and correct" means for moving this feature to a new accelerator (and/or a new CPU tier),
with the thresholds the project already enforces and the values measured on the reference box
(`measured-costs.md`) so each criterion has a number attached. Ordered strictest first: a port that
fails an earlier level cannot be validated by the later ones.

Harnesses added for this document (all runnable now):

| script | level | output |
|---|---|---|
| `notes/verify_trellis.py` | A (format) | [1]-[5] format checks |
| `notes/acceptance_kernel.py` | B (kernel numerics) | CPU vs fp64 oracle vs GPU reconstruct, bitwise repeatability |
| `notes/acceptance_model.py` + `notes/acceptance_report.py` | C (model agreement) | KL / top-1 / greedy table with pass-fail under the suite's own policy |
| `notes/run_profile_ab.sh` | C, E hygiene | cold vs warm placement start |
| `notes/bench_handoff.py`, `notes/bench_cpu_moe.py`, `notes/bench_link.py`, `notes/prof_e2e.py`, `notes/run_e2e.sh` | E (performance) | per-hop, per-tier and end-to-end costs |

---

## Level A — the weight format must be **bit-exact**

No tolerance is acceptable here: `reconstruct`, the GEMV/GEMM kernels, the CPU worker and the
un-swizzle kernel all read the same bytes, so a bit-order deviation is silent corruption, not noise.

Required properties, each with the check that proves it (details in [`mul1-trellis.md`](mul1-trellis.md)):

| # | property | check | expected on the reference data |
|---|---|---|---|
| A1 | window = ring bits `[S(i)-16, S(i))`, tail-biting, MSB-first, `uint16` pairs forming big-endian-bit `uint32`s | `testlib.trellis.is_tail_biting(unpack(packed, K), K)` on a real expert tensor | `True` at K=3 and K=2.5 (`verify_trellis.py [1]`) |
| A2 | tile element order = tensor-core permutation | independent NumPy dequant vs `ext.reconstruct` | max abs diff **0.0** on `(2560, 640)` expert weights, both rates (`[2]`) |
| A3 | mul1 codebook = `fp16((bytesum(s·0x83DCD12D) − 510) · fp16(0x1eee))`, one rounding | enumerate all 65536 states | **913** distinct values, range `[-3.4531, 3.3477]`, mean `-0.0019`, std `1.0003`, largest collision class 175 (`[3]`) |
| A4 | half-integer rates: `D(i) = KA + bit(i mod 16) of 0xAAAA`, tile = `16K` `uint16` | A1/A2 at K = 1.5 / 2.5 / 3.5 | covered by `tests/moe_cpu/test_half_rates_cpu.py`, `tests/kernels/moe/test_moe_half_rates.py` |
| A5 | packed CPU layouts (band-g, planar dwords) round-trip, and the *rule* is per-tier | `repack` → inverse → compare | equal for K = 1, 2, 2.5, 3, 8 with this tier's `(group, planar)` = `(2, 1)`, `(2, 1)`, `(0, 0)`, `(2, 1)`, `(2, 1)` (`[4]`) |
| A6 | int8 fusion identity (`Σ w·x = k_inv·q·(Σ bytesum·x8 − 510·Σx8)`) | dot-product check | agrees to fp16 rounding, rel err 3.3e-4 (`[5]`) |
| A7 | dims are multiples of 128 after padding; `k ≤ 8192` for int32 accumulators | loader assertions (`moe_mul1.cpp:3668-3674`) | assert, don't assume |

**A new backend must not re-derive any of this**: `tests/testlib/trellis.py` is the executable spec
(pack/unpack/decode/dequant/dense-linear in float64, no extension calls) and should be ported with
the kernels; every format test in `tests/kernels/quant/` treats it as ground truth.

## Level B — the CPU expert kernel's numerical class

The CPU path is allowed to differ from the GPU path (int8 activations, fp32 transforms, different
accumulation order), so the criterion is *error against exact arithmetic on the same quantized
weights*, plus internal consistency.

Existing bars in the tree (do not weaken them):

| test | bar |
|---|---|
| `tests/moe_cpu/test_tiers.py` | every int8 tier within **rel L2 0.05** of the fp32 `scalar` tier (`SCALAR_TOL`), and tiers mutually consistent |
| `tests/moe_cpu/test_half_rates_cpu.py` | per-row error **< 0.04** at each rate, swizzled and native |
| `tests/moe_cpu/test_wide_rows.py` | **< 0.04-0.05** on inputs with a dominant shared component; deep-saturation activations must stay **finite** |
| `tests/moe_cpu/test_cpu_decode.py` | single-token fused finish == batched path (exact same arithmetic, so compare tightly) |

Measured class of the current implementation (`notes/acceptance_kernel.py`, real expert weights,
activations either real captured hidden states or `randn` with a massive shared component; error is
relative L2 of the routed sum against a float64 reference built only from `testlib.trellis`):

| model / rate | rows | input | CPU rel RMS | GPU reconstruct rel RMS | CPU/GPU | CPU bitwise repeatable |
|---|---|---|---|---|---|---|
| Qwen3.5 @K=3 (band-2+planar) | 1 | synthetic+massive | 1.82e-2 | 8.36e-4 | 21.8 | yes (30 reps) |
| | 4, 16 | **real** | 1.45e-2, 1.50e-2 | 8.0e-4, 7.95e-4 | 18.1, 18.8 | yes |
| Qwen3.8 @K=2.5 (native) | 1, 4, 16 | synthetic | 2.00e-2, 2.16e-2, 2.10e-2 | 8.3-8.7e-4 | 24.2-24.8 | yes |

**Gate B1:** rel RMS against the fp64 oracle ≤ **2.5e-2** per layer for the above shapes, i.e. within
the ~1.5-2.2e-2 band the int8 scheme already occupies, and comfortably inside the suite's 0.04 bar.
**Gate B2:** the ratio to the device reconstruct path ≤ **~25×**; a port that beats 1e-2 has changed
the algorithm (finer activation quantization) and must say so.
**Gate B3:** repeated calls with identical inputs are **bit-identical**. The CPU scheduler steals
work units, so this is a real invariant (per-unit arithmetic must not depend on the worker), and it
is what makes greedy replay debuggable.
**Gate B4:** tier agreement — if the port adds a new ISA tier, it must land inside 0.05 of the
existing tiers, and the *layout rule* (`swizzle_group`, `planar_layout`) must be reported per rate
(the AVX2 tier leaves half rates native; the AVX-512 tiers band them; a new target must state its
own table and have the GPU restore side read it, never duplicate it).

## Level C — whole-model agreement (the project's own tolerance policy)

Policy, from `tests/testlib/e2e.py::assert_logits_agree`: per-position KL(P‖Q) with
`median < max(abs_median_kl, 4 × noise_floor_median)`, `mean < max(0.05, 4 × floor_mean)`,
**confident top-1 ≥ 0.97** over positions where the reference leads by > 1.0 logit, and all logits
finite. `tests/e2e/test_moe_offload.py` sets `abs_median_kl = 1e-2` for the CPU path (its docstring:
"The CPU path's int8 activations add error on top of the routing noise floor").

Measured against an all-GPU load of the same weights (Qwen3.5-35B, 193-token teacher-forced prompt,
24 cached decode steps, **cold placement start**, `notes/m_accept_report2.txt`):

| placement | teacher-forced KL med / mean / max | cached prefill+decode KL med / mean / max | confident top-1 | greedy (24 tok) |
|---|---|---|---|---|
| `-mcs 192` | 7.09e-4 / 1.15e-3 / 1.52e-2 | 4.85e-4 / 1.45e-3 / 1.87e-2 | 1.000 (114 pos) | identical |
| `-mcs 192 -mcpa` | 4.93e-4 / 1.10e-3 / 3.03e-2 | 3.17e-4 / 1.46e-3 / 1.62e-2 | 1.000 | identical |
| `-mcs 192` `WIDE=0` | 5.03e-4 / 1.04e-3 / 3.09e-2 | 4.57e-4 / 1.16e-3 / 7.64e-3 | 1.000 | differs at token 4, reference lead **+0.234** → allowed near-tie |
| `-mcl 20` | 5.09e-4 / 1.13e-3 / 2.75e-2 | 3.52e-4 / 8.79e-4 / 8.88e-3 | 1.000 | identical |

The model's own noise floor in the same run: median `2.43e-4`, mean `3.07e-4`.

**Gate C1:** median KL ≤ 1e-2 (the suite's CPU bar). Measured headroom **14-32×** against 1e-2, and
**2.8-6×** against the *generic* 2e-3 bar — so a port that merely matches the current path passes
both, and anything landing above ~2e-3 median needs justifying.
**Gate C2:** confident top-1 = 1.000 measured; the bar is 0.97. A real expert-mapping or staleness
bug produces KL of **order 1** (per `test_moe_offload`'s docstring), i.e. this gate is not marginal.
**Gate C3:** the same three measurement paths must pass: cache-less teacher-forced forward, cached
prefill + single-token decode (this is the one that exercises the decode handoff), and batched
decode (in the suite; `prefill_decode_logits` accepts a list of sequences).
**Gate C4 (not required):** greedy trajectory equality. It happens to hold here for `-mcs` and
`-mcl`, but the contract is statistical agreement: `WIDE=0` diverges at a 0.234-logit near-tie and
that is legal. Do not add a greedy-equality gate without also pinning the placement profile.
**Prerequisite:** placement state must be controlled or these numbers are meaningless —
`measured-costs.md` §8.3 shows the hot-expert profile is keyed on model dir + expert count only, is
rewritten at unload, and changes decode throughput 12-22% and the CPU hit count 25%. Redirect
`block_sparse_mlp_cpu.EXPERT_STATS_DIR` (what `tests/` does) or pass
`EXL3_MOE_CPU_SPLIT_STATS`, and say in the report which state was used.

## Level D — protocol and liveness invariants

Each of these has a test in the tree; a port must keep the behaviour, ideally the test.

| invariant | why it bites | existing test |
|---|---|---|
| Descriptor is host-visible **before** the GPU publishes `data_ready`; sequence increases monotonically | child reads a torn/old descriptor | `tests/kernels/moe_cpu_host/test_moe_worker.py`, `test_moe_flags.py` |
| 32-bit flags compared **cyclically**; 64-bit where the backend's wait is a plain `>=` | wrapped flag satisfies a wait early | `test_moe_flags.py` (+ `MOE_FLAG_BITS` note in `moe_handoff.h:44-52`) |
| Slot reuse gates on `consumed` (written by the *reading* stream), not `done` | multi-device: worker overwrites an output another device has queued | `test_moe_worker.py`; reasoning in `moe_handoff.h:26-33` |
| Issue window ≤ `num_slots` with inline collect | in-stream deadlock (the historical "second-prompt freeze") | `tests/e2e/test_moe_offload.py` (two prompts in one session) |
| Ring-full throttle: `exl3_moe_split_issue_fused` returns false without side effects, caller polls `jobs_head` | long prefill overflowing 256 jobs | `test_moe_worker.py` |
| `COMPUTE_GATED` jobs may skip compute **and** the readback; plain `COMPUTE` must always write/zero the output | collect reads garbage for an all-`-1` job | `tests/kernels/moe/test_moe_split.py` |
| Dead-worker detection: memop waits have no timeout, so the host watchdog unblocks them | hung stream instead of an error | `moe_cpu_host.py:1310` `_start_watchdog`; exercised by kill tests |
| Uniform `hi`/`ho`/`topk` across registered layers; all boundary copies contiguous | strided host copies are executed eagerly at enqueue time | `ensure_started` assert (`moe_cpu_host.py:1200`) |
| Pinned/registered memory: handoff segment registered **after** arena chunks, with chunk release-and-retry if the pinned budget is exhausted | OOM-in-registration on WDDM/WSL2 | `tests/moe_cpu/test_pinned_arena{,_windows}.py`, `_register_handoff` |

## Level E — performance gates

Floors, from `measured-costs.md`, with the tolerance a port should hold itself to (±30% is the
suggestion where the mechanism is protocol-bound, since those costs are launch/latency dominated):

| gate | reference value | why |
|---|---|---|
| E1 empty (all-`-1`) decode job | **20 µs/layer** (48-job pipeline: 13-19 µs) | the floor for cold tails; if the port's handshake is slower than this, layer count multiplies the loss |
| E2 flag round trip host↔device | 6.4 µs (memops) / 10.7 µs (kernel), enqueue 1.8 µs | per-layer, twice |
| E3 issue + collect kernels at decode | 3.9 + 4.0 µs each, 1 row; ~21.6 + 41.3 µs as `copy_` at 64 rows | the payload movers |
| E4 CPU layer cost | `experts × expert_bytes ÷ DRAM read rate` with the measured rate for the actual tier (47.4 GB/s @K=3 packed, 31.1 @K=2.5 native, 15 threads) | bandwidth-bound: measure cold selections, never a repeated one |
| E5 pinned→device sustained | 13.3 GB/s here (Gen4 **×8**); unswizzle ~440 GB/s effective; stage `memcpy` 16.3 GB/s + ~175 µs per job | prefill is link-bound: 28% of device time is this DMA |
| E6 end-to-end, placement-controlled | `-mcs 192` warm ≈ 100 tok/s decode / 1790 prefill; `-mcs 192 -mcpa` ≈ 78 / 2523; `-mcl 40` 54.5 / 1401; all-GPU 124 / 5043 (Qwen3.5, this box) | regressions must be explained by E1-E5, not by noise |
| E7 streaming must dominate the tail | turning streaming off costs **2.1×** at 2048 rows | if a port makes streaming cheaper than 2.1× better than CPU tail, `stream_t` is wrong |

Measurement hygiene that these gates depend on: rotate expert selections (L3 is 64 MiB and will
otherwise absorb the whole working set); use real text routing for anything placement- or
threshold-sensitive (random ids wash the profile effect out); warm up before timing; report profiler
numbers separately (`EXL3_SPLIT_PROF`/`HANDOFF_PROF` cost ~30% on their own); state link geometry
(gen **and** width, measured under load) with every bandwidth figure.

```bash
# C - model agreement (cold and warm placement, both reported)
python notes/acceptance_model.py $MODEL --placements ref,split,split_pa,layer20 \

python notes/acceptance_report.py /tmp/m1.pt
# D - the suite
pytest tests/moe_cpu tests/kernels/moe_cpu_host tests/kernels/moe -m "not slow"
pytest tests/e2e/test_moe_offload.py tests/e2e/test_moe_stream_unswizzle.py -m slow
# E - performance
bash notes/run_e2e.sh split192 split192pa layer40 streamT0 && bash notes/run_profile_ab.sh
python notes/bench_link.py; python notes/bench_handoff.py $MODEL --experts 256
```

A port is accepted when A is bit-exact, B1-B4 hold, C1-C3 pass with the placement state declared,
every Level-D invariant has a passing analogue on the new backend, and E1-E7 deltas are either
within tolerance or explained by a measured mechanism.

## Explicit non-goals

- **Bit-exact CPU/GPU parity** — impossible by construction (int8 activations, fp32 transforms,
  different accumulation order); Levels B/C measure the *distribution* of the difference instead.
- **Greedy-token equality** across paths (Gate C4), and bit-identity across `EXL3_MOE_RECON_FOLDED`
  modes (the docs note those are "equally far from the baseline", not closer).
- **Determinism across slot/ring geometry changes**: `SLOT_ROWS`/`SLOTS` change chunking, hence the
  number of jobs, hence nothing about arithmetic — but placement and atomics do change results.
- **Porting the tuning defaults**: `stream_t`, `STREAM_FUSED_T`, `SLOT_ROWS`, `WSLOT_MB` and the
  swizzle tier table are all calibrated to *this* silicon; the port inherits the *procedure*
  (`measured-costs.md` §9), not the numbers.

# B70 offload: expert kernels

What has to be written for the arithmetic itself. Two references carry the requirements:
[`doc/prep/mul1-trellis.md`](../prep/mul1-trellis.md) (the format, its invariants and the integer
fusion identity) and [`doc/b70/EXL3 mul1 Trellis Unpacking on Arc Pro B70 — Cheat Sheet.md`](../b70/)
(the Xe2 recipes, which were re-derived from `cpu/moe_mul1.cpp` and checked exhaustively). Facts
about the card are from `notes/b70/` **[M]** or from `b70-bench`'s measured peaks; anything marked
**[P]** is a budget, not a measurement.

## 0. Contract

One job = one layer's routed-expert contribution for `rows` tokens, exactly the CPU worker's
contract (`exl3_moe_cpu_forward_raw`, `cpu/moe_mul1.cpp:3801`):

```
in   x8[rows(or 2·rows wide), hi] int8   q[], sum_x8[], wide[]        (produced by the 3090, §5)
     sel[rows·topk] i32 (-1 = handled by the parent GPU)   w[rows·topk] fp16
     per expert, per projection: trellis tiles in B70 VRAM (§2.2 layout rule), suh/svh/bias
out  out[rows, ho] fp32  (accumulated, weighted, in place — the slot is not read by anyone else)
```

Invariants carried over verbatim, asserted at load rather than assumed (`doc/prep/mul1-trellis.md`
§1, §6, A7): tile = 16×16 weights; ring = `256·K` bits in `16·K` `uint16`, `uint32` words little-
endian with bit 0 at word 0's MSB; window = 16 bits ending at `S(i)`, tail-biting; element order =
`tile_perm`; `k`/`n` multiples of 128 after padding; every expert inside a layer shares one rate
(assert it — the prep README notes nothing currently enforces it); `k ≤ 8192` for the int32
accumulator bound (Xe2 is actually safe to 16 825, keep the stricter cap so both backends see the
same inputs).

## 1. Budget that decides every design choice here

| resource | figure | consequence |
|---|---|---|
| VRAM read, measured on this exact access pattern | **132–292 GB/s scattered, 216–558 GB/s clustered** (608 GB/s spec; `probe_rates`, **[M]**; the range is working-set size, 64 MiB–2 GiB — `out_rates_footprint.txt`) | 351–919 G-weights/s scattered at K = 2.5–3.0; the spread is *ordering* and *footprint*, not layout — §3a |
| lanes × clock | 4096 × 2.8 GHz = 1.15·10¹³ lane-ops/s | the real unpack density (+47 lane-inst per 32-lane word) costs 0.1–4.4 % of bandwidth at decode-like footprints, 14 % at a 64 MiB one — decode sits on the bandwidth side of that line, with less margin than the first measurement suggested |
| XMX | 183 TFLOP/s fp16, 367 TOPS int8 **[M]** (`b70-bench`; integer DPAS measured at 366.92 TOPS = 100 % of spec, and `dpas.hpp` allows u8×s8→int32) | against the measured 674 GB/s copy peak that is **272 MAC per byte** *for a 1-byte-per-weight format* — at our 0.375 B/weight with 4 byte-MACs per weight-token (b70-kernels.md §2c item 13b) the same arithmetic gives **~26 rows per expert**, or ~59 against the 292 GB/s the GEMV really gets; §4a carried the 272 number into a prefill eligibility claim and needs re-running, while decode is unaffected because at 5–6 rows/expert the limiter is instructions per row, not the matrix unit (§3b) |
| SLM / L1 | 128 KiB per Xe core (driver-reported **[M]**), 18 MiB L2 | a Qwen3.8 decode job reads ~12 MiB, comparable to L2 — see §3a item 4 |
| subgroup | 16 and 32; DPAS wants 16 | lane = output column = exactly the trellis permutation (§2.3) |

The earlier draft of this table said the decode kernel "lives or dies on ops per weight" and made
verifying the int8 dot's instruction count a phase-1 gate. Measurement overturned that: at realistic
density (extract + multiply + accumulate, ~10 weights per u32, **+47 lane-instructions per 32-lane
word = per 128 B of stream**) the loop loses **4.4 %** of bandwidth on Qwen3.8's geometry and **0.1 %**
on GLM's versus the same reads with no arithmetic, and `dot_acc` versus a manual 3-mask/3-shift/3-add
byte sum differ by **0.2–0.4 % — not measurably** (**[M]**, `probe_rates` R6/R7, reproduced across
three independent runs in `out_rates_repeat.txt`). Breaking the accumulator into 8 independent chains
makes it 1.2–1.4 % *worse*, so the residual is instruction count and register pressure, not dependency
latency. Decode on this card is bandwidth-bound, so
the dot earns its place on instruction count and energy, not on throughput, and it is no longer a
design risk. Op count still matters where arithmetic is heavy against bytes: the XMX routes (§4), and
Recipe A (~6 ops/weight) versus Recipe B (~4) on the half-rate layers, where 3.2 weights per byte
leave less headroom — re-measure at real density in phase 2 rather than assuming either.

Three rules from the probes, because all three fail silently: index with `i[0]` and cast
explicitly (`p[i] = seed + i` on a `sycl::id<1>` compiles, runs, reports success and stores nothing —
`notes/b70/LESSONS.md` 4a), and no `sycl::atomic_ref` on the shared region at any scope (it loses the
device, `LESSONS` 4). Publish results as: stores → `sycl::atomic_fence(acq_rel, system)` → flag store.

## 2. Trellis decode

### 2.1 Recipe A — universal, all rates
The `funnel_r` form from the cheat sheet: end bit `e = ((t+1)·(2K+hb))>>1`, first bit wraps via
`e + L − 16` when `e < 16`, and the two-word funnel never shifts by 32. Use it for
`K ∈ {1.5, 2.5, 3.5}` (half rates break the word alignment Recipe B needs) and as the *reference
implementation* every other path is diffed against. Qwen3.8's 2.5 bpw layers — the majority of that
model — are in this class, so Recipe A is not a fallback corner: it needs its own throughput number.

### 2.2 The three traps, each as a test
1. **shift by 32**: OpenCL masks the count, C++ is UB; the naive `(lo>>s)|(hi<<(32−s))` corrupts
   8/256 states at odd K, 32/256 at K=4, 64/256 at K=8. Test: every state of every K, against
   `tests/testlib/trellis.py`.
2. **tail-biting wrap**: state 0 borrows the tile's last bits; index `mod 8·K`, never clamp. Test:
   `is_tail_biting` on real expert tensors (Level A1).
3. **byte/half order** inside DPAS operands and inside the `uint16` pairs. Test: the K=4 vector
   table in the cheat sheet (six `(r,c)` triples with their state, product, byte-sum and weight),
   as a device unit test, plus `(0,0)` being the wrap case.

### 2.3 Recipe B — integer K, SG16, lane = column
`trellis_column()` loads `K+2` words per lane, realigns once by `4K·h` bits, then extracts 16 states
with compile-time indices/shifts (~4 ops/state). Two things make it worth more than the ops saved:
the produced column-per-lane layout **is** the DPAS B-operand layout, so the prefill path consumes
it without a shuffle or an SLM round trip, and `raw[]`/`a[]` stay in registers — which is only true
if `zeKernelGetProperties.spillMemSize == 0`, checked by the harness at build time for every shipped
kernel and every K (the cheat sheet warns K=8 is where it breaks).

### 2.4 Weight value
Never materialise a float weight. `bytesum(state · 0x83DCD12D)` is accumulated as an integer; the
affine epilogue `k_inv·q·(acc − 510·Σx8)` is applied once per output. Two consequences: the −510
correction needs the per-row `Σx8` (§5), and the fp16 form `(half)(bytesum − 510)` is *exact*
(|v| ≤ 510 < 2048 with 11 mantissa bits), which is what licenses the XMX routes in §4.

## 2a. What the shipped kernels spend per weight — read this before writing another GEMV

`probe_gemv.cpp` runs the real operation (checkpoint trellis bytes, the `moe_mul1.h` identity, output
bit-exact against `tests/testlib/trellis.py`) and it says the model in §1 was wrong about which resource
binds. Two revisions, both measured at 512 experts / 300 MiB / R = 1 (**[M]**, `out_gemv.txt`):

| inner loop | lane-ops per weight | GB/s | instruction model (1.43·10¹² SIMD inst/s ÷ ops per byte) |
|---|---|---|---|
| rev A: per-window address math, 64-bit shift, manual 3-shift/3-add byte sum | ~17 | **27.9** | 31.6 |
| rev B: grouped dword-pair extraction + `dot_acc` byte sum | ~8 | **61.4** | 67.2 |
| the byte stream itself (`probe_rates`, same tiles, no arithmetic) | ~0 | **287–292** | — |

The model tracks the measurement to within 10 % at both points, and the 250–292 GB/s figure the whole
decode budget rests on is the *third* row — reachable only by a kernel that spends almost nothing per
weight. That is exactly what the CUDA and CPU paths do:

* **CUDA** (`quant/exl3_gemv_int8_kernel.cuh`, `ext4w`/`ext8w` + the accumulator loop): two dword loads
  serve 4–8 consecutive ring windows, each generated by one `fshift(b, a, s + k·bits)` with the address
  math hoisted and the bit offsets compile-time constants; the window becomes
  `prod = window * 0x83DCD12D`, and **each token row costs exactly one
  `dp4a_us(prod, splat(a_int8), acc)`** where `splat` is `0x01010101 * x8` precomputed in shared memory
  (line 274). Byte-sum, multiply and accumulate are one instruction; nothing is ever materialised.
* **CPU** (`cpu/moe_mul1.cpp`): same identity, `vpdpbusd` per 16 weights; for multi-row it first folds
  byte-sums into i16 lanes so one `vpmaddwd` returns `bytesum × x` for **two rows** (lines 322, 1038,
  1146) — a cheaper per-row marginal cost than one dot per row, and the model for what to do at b ≥ 2.
* **ROCm** keeps a third variant worth reading before committing (`rocm/quant/exl3_gemv_tiles_rdna.cuh`),
  since RDNA's dot-product support differs from both.

Transplant to Xe2, in order of value:

1. **Stop materialising byte-sums.** rev B stages `bs[]` into SLM and then does load+load+mul+add per
   (weight, row) — which is why its rate falls 61 → 13.8 → 4.6 GB/s at R = 1 → 8 → 32 and collapses to
   0.2 at R = 128 (register spill from the accumulator array). Hold `prod` in a register and do one
   `sycl::ext::oneapi::dot_acc(prod, splat_row, acc)` per (weight, row): that is ~2 + R instructions
   per weight instead of ~8 + 4R. This toolchain *does* have the primitive —
   `sycl/ext/oneapi/dot_product.hpp` provides `dot_acc(uint32_t, uint32_t, int32_t)` plus the mixed-sign
   `vec<uint8_t,4>`/`vec<int8_t,4>` overloads, which is what `dot_4x8packed_us_int` is sugar for on
   newer drivers.
2. **Pre-splat activations** into `0x01010101 * x8` (uint32) in SLM, exactly as CUDA does, so the dot
   needs no separate scale step. Cost is 4× the SLM bytes for `x`, which §1 says is free.
3. **Grouped extraction with constant shifts**, as rev B now does: ~10 ring positions share one dword
   pair at K = 3 (`while off + 16 + 3t <= 64`), one address computation per group. SYCL has no funnel
   shift (`grep -l funnel $SYCL_INC` → nothing), so write the idiom `(hi << s) | (lo >> (32 - s))` and
   let LLVM form `fshr`, or copy CUDA's chain (`w6 = w7 >> (KA+1); w5 = w6 >> KA; …`) which needs no
   funnel at all.
4. **Then, and only then, does ordering matter.** At rev A/rev B instruction counts the clustered and
   scattered grids measure the same within 1.5 %; §3a's locality rules are still right, but they are the
   *second* problem. E4b must be judged after E4's instruction budget is met.

This also retracts two claims that §1 and `b70-architecture.md` §12 previously carried as settled: the
dot-instruction question was **not** answered behaviourally by `probe_rates` (a proxy that computes no
weights cannot bound the cost of the arithmetic it omits — it walked the same bytes at ~1 op per weight
and reported 292 GB/s), and "decode is bandwidth-bound" is a property of the *byte stream*, not of the
kernel. Both are open again, behind E4.

## 2b. Rules lifted from `doc/b70/llm-scaler` — Intel's own XPU MoE kernels, with their perf post-mortems

`doc/b70/llm-scaler/sglang/custom-esimd-kernels/csrc/` contains production ESIMD MoE kernels for the
same hardware generation (Q4_K/Q5_K/Q6_K grouped GEMV, batched decode GEMV, DPAS prefill, fused
bucket/topk), and several files carry annotated *why the first version was slow* notes with numbers.
What they say that changes our design:

1. **Wide, LSC-granular loads; one flat accumulator; fold once.** `moe_kquant_GEMV.h`: the original
   "stepped 32 at a time, issuing 16-byte nibble loads (below LSC granularity) and re-reading a scalar
   scale/min per block", and folding "a full horizontal sum … into a serial `dot` chain every block" —
   it "only reached ~180 GB/s"; widening the tile and removing the per-block reduction is what fixed it.
   `q8_0_GEMV.h` states the reason outright: a per-iteration `reduce<>()` would cost
   "M × K_ITERS cross-lane reductions (128 per work-item at M=4, K=2048) whose shuffles do not produce
   useful FLOPs, and **this kernel is ALU bound, not bandwidth bound**" — an independent confirmation of
   what `probe_gemv` measured on our trellis.
   → Rev C: `simd`-width tiles (≥32 B per load), accumulate lane-parallel into `simd<int32_t, VL>`,
     one `reduce` per output at the very end. Never reduce inside the k loop.
2. **~180 GB/s is the realistic ceiling for a mature MoE GEMV on this class of card**, not the
   292 GB/s bare-stream rate. → **Superseded by measurement, and the units were wrong.** Rev C reaches
   116.4 GB/s at E=512/R=1 and 76.6 GB/s at the b=1 shape (§2b item 9). At 3.0 bpw those are **309.5 and
   204 G-weights/s**, against Intel's q8_0 GEMV at ~470 G-w/s (1 B/weight) and their narrow K-quant
   shapes at 120–180 G-w/s — so the trellis kernel already sits above their narrow-shape rates, and
   GB/s was never comparable across formats with different bytes-per-weight. At 165 GB/s the planning
   figure had been 91 µs/layer for Qwen3.8 b=1; at the measured 76.6 it is ~195 µs.
3. **Amortise the activation load across output columns.** `moe_kquant_GEMV.h`: with one column per
   work-item, "every work-item re-reads `inter` in full (N=2048 work-items × 512 B = 1 MB of cache
   traffic per route for a 4 KB tensor)"; handling `ROWS>1` columns per work-item removed it. My rev B
   has the same defect in SLM form (each item reloads `xs[]` per weight).
4. **Grid order for L2 reuse across row-tiles**: `q8_0_GEMV.h` lays groups out **M-tile-fastest** "so the
   MT groups that share a weight row block are adjacent: tile mt+1 then finds that block still in L2
   instead of re-pulling it from memory." Same family of rule as §3a, and it applies to our
   multi-row/multi-chunk decomposition too.
5. **Row tiling is bounded by GRF, and by the compiler, not by taste**: "M=4/VL=256 fits;
   M=8/VL=256 is what the AOT gen compiler refuses to lower", and the m-loop "must stay fully unrolled
   (`vacc[m]` needs a compile-time index)". This matches `probe_gemv`'s collapse at R = 128 — the answer
   is to tile rows **in the grid** (their `MT`) with M ≤ 4 in-kernel, not to widen the accumulator array.
6. **They bucket by expert and fold the gather into the load.** `moe_q4k_ggemv.h` takes
   `chunks = {eid, t0, nt}` (route-sorted ranges) and an optional `tok_ids` permutation so the kernel
   "reads the activation directly from `expert_states` at row `tok_ids[t0+m]` — folding the per-expert
   input gather INTO the load (no `index_select` round-trip)". Two consequences for us: the §3b schedule
   should look like this, and — important — their *decode* GEMVs are **per-route**
   (`grid = (n_routed, n_col)`), i.e. they do **not** dedup an expert across routes and rely on L2.
   Our entire concurrency model assumes the union (`bytes = union(rows) · expert_bytes`); that is only
   true if we bucket, so bucketing is a *correctness precondition* of the byte model, not an optimisation
   — without it the b=8 footprint is 8× worse than modelled.
7. **Repack for dequant ergonomics is a different question from repacking for locality.** Their formats
   are stored as an interleaved nibble plane plus a *plain* high-bit plane (`qh`, "byte j bit b = elem
   8j+b") plus fp16 scale/min per 32, specifically so the inner loop is wide and mask-free
   (`v5 = nibble | (qh << 4)`). `b70-architecture.md` §2.2's null result (banded/native 0.96–1.05×)
   tested locality-driven repacking only; a dequant-driven repack is untested and is the kind Intel chose.
8. **DPAS tiles are chosen by wasted lanes, not by arithmetic intensity.** `moe_q4k_ggemv.h` is
   instantiated at `MS_=4` (64-token tiles) for prefill and `MS_=1` (16-token) precisely because "for
   SMALL M (e.g. MTP verify M=4) the 64-row DPAS wastes ~60/64 rows". So the real rule for our §4 is
   *tile height ≤ rows per expert*, with the GEMV preferred below ~16 — which is much more aggressive than
   the 272-row arithmetic-intensity crossover, and consistent with the `…CACHE-MISS / JIT-recompile`
   warning in `q8_0_GEMV.h` about falling back to oneDNN `jit:gemm:any` per new `(M,K,N)` shape. Our
   engine must own every shape it uses, and the XMX/GEMV decision is a per-(M,K,N) table, not one number.
9. **Two driver-level hazards, both already biting us.** Cross-subgroup SLM exchange needs the full
   barrier: "a named barrier only orders execution, it does not make the SLM stores visible to the other
   subgroups, so the split arrive/wait form leaves the exchange racy; `barrier()` carries the required
   memory fence" — our groups are 64 items = 2 subgroups sharing `bs[]`, so this is live, not theoretical.
   And unclamped tail addressing "is an out-of-bounds device read (observed as
   `UR_RESULT_ERROR_DEVICE_LOST`)" — same failure signature as `LESSONS` 4, reached from a different
   direction: on this driver an OOB *read* does not fault verbosely, it kills the device.

# B70 lessons — mistakes made once, so they are not made twice

Everything here was hit in this repository while probing, and every claim is backed by an
experiment in this directory. Ordered by how much time each one cost.

## 1. `.wait()` is not a completion mechanism, it is a 24 µs tax

`sycl::event::wait()` / `sycl::queue::wait()` on this stack cost **~24 µs** even for an empty
kernel. Measured on the same work: submitting a kernel whose only job is to write a flag in
page-locked host memory, and spinning on that flag host-side, completes in **5.0–6.3 µs**. The
first version of `probe_transport.cpp` timed *everything* with `.wait()`, so every copy and every
launch looked like a 24 µs operation and the whole "resident kernel" idea looked like it was worth
8×. It is worth ~2×, and only for the handshake.

Rule: the hot path never calls `.wait()`. Completion is a flag in pinned memory that the parent's
CUDA stream waits on with `cuStreamWaitValue32` (the existing protocol), or that the B70 engine
thread spins on. `.wait()` is for setup and teardown only.

## 2. A parked kernel does not see host writes unless you fence it

`volatile` on the host pointer is *not* enough. A loop reading a host-pinned word from a resident
kernel returns the value it cached on entry, forever — no error, no progress, the host just waits.
It cost a full debugging cycle to find, because the symptom (kernel runs, host writes, nothing
happens) looks like a submission problem.

```c++
uint32_t cur = *(volatile uint32_t *) db;                                  // may be stale
sycl::atomic_fence(sycl::memory_order::acq_rel, sycl::memory_scope::system);   // this is what works
```

`probe_resident.cpp` prints an entry/heartbeat marker precisely so "never started" and "started but
cannot see the doorbell" are distinguishable. Keep that pattern in any B70 test.

## 3. Divergent polling lanes in one work-group do not work; keep control flow uniform

On Xe a work-group is executed as SIMD lanes of one hardware thread. The first resident kernel
branched (`if (local_id == 0) poll_and_ack(); else spin_elsewhere();`) and never completed a round
trip, in every configuration, including 1 group of 32 lanes. The corrected shape:

* every lane runs the same loop;
* lane 0 performs the host read (`sl == 0 ? *db : 0`), the value is broadcast with
  `sycl::select_from_group(sg, cur, 0)`;
* work is spread across the sub-group by striding on the local id, never chained in one lane.

Related: `fetch_add` on a host flag must be issued at a **uniform call site**
(`aack.fetch_add(sl == 0 ? 1u : 0u)`) — the same divergence rule applies to cross-device atomics.

## 4. A `sycl::atomic_ref` on *foreign* (registered) host memory takes the device down

Any scope. `probe_stores.cpp` used `atomic_ref<uint32_t, relaxed, memory_scope::device>` on a
`register_host_memory` pointer and the next call returned
`level_zero backend failed with error: 20 (UR_RESULT_ERROR_DEVICE_LOST)` — the *device* was lost, not
just the queue. With `memory_scope::system` the same mistake was quieter: `wait()` returned success,
nothing had been written, and the poisoned queue made the *next*, unrelated kernel also silently
write nothing (that is how test A4b failed until the cause, three tests earlier, was fixed).

Publish flags with `sycl::atomic_fence(acq_rel, system)` + a plain volatile store instead: that is
measured to work, in-process and cross-process, and the 3090's `cuStreamWaitValue32` retires on it
(`probe_cross.py` A3a/A3b, `probe_crossproc.py` X1/X3). Plain kernel stores into the same region are
also fine and reliably visible — 100 repetitions across five patterns, cold and host-dirtied lines,
with and without a following fence, registering 5 pages or 4 MiB, and before or after
`unregister_host_memory` (`probe_stores2.cpp`, `probe_unreg.cpp`).

Corollary for every B70 test: **assert that the payload landed, never only the flag.** A test that
checks a flag and a return code passes happily while 16 KiB of results are missing.

## 4a. Kernel index arithmetic (the expensive one): spell `i[0]` out, or the kernel silently writes nothing

The single most expensive bug in this directory. This compiles, runs, returns success, and does not
write anything:

```c++
uint32_t *p = (uint32_t *) ptr;
g_q->parallel_for(n_words, [=](sycl::id<1> i) { p[i] = 0xC0FFEE00u + i; });   // payload stays ZERO
g_q->single_task([=] { ...fence...; *(volatile uint32_t *) (p + n_words) = seq; });  // this lands
```

`sycl::id<1>` has an implicit conversion to `size_t`, so the expression type-checks; the kernel is
accepted by the compiler, submitted, completes without error, the *neighbouring* word written by the
next command is visible to the host, and the payload itself is never stored. Writing it the
explicit way

```c++
g_q->parallel_for(n_words, [=](sycl::id<1> i) { p[i[0]] = 0xC0FFEE00u + uint32_t(i[0]); });
```

stores every word, first time, in every memory type tried. The `+=` (read-modify-write) form of the
sloppy expression happened to work, which is what made it take so long to find: the first probe that
looked correct (A1) masked the pattern that did not (A3a), and the failure then looked like a PCIe
coherency problem, sending two full probe rewrites down that path (`probe_coherency.cpp` is kept as
the artefact that *disproved* the coherency theory).

Rules adopted: index with `i[0]` / `it.get_global_id(0)` and cast to the value type explicitly; never
mix `sycl::id` into arithmetic; and give every kernel test a "wrote it, read it back, compared every
word" assertion.

Related: `sycl::malloc_host` memory (allocated by the xe driver) and memory brought in with
`register_host_memory` are *not* equivalent: the former accepts atomics, the latter does not, and
only the former is refused by `cudaHostRegister` (item 8). Nothing in the design should depend on
either being interchangeable.

## 5. `register_host_memory` requires a whole number of host pages

`register_host_memory: size must be a multiple of the host page size` — and the pointer must have
that much memory mapped behind it, so round the length up **and** give the region slack. The
parent's handoff segment is page-backed, so this only affects ad-hoc tests.

## 6. Only one lane per group may poll across PCIe

With 32 work-groups × 32 lanes all polling the doorbell, a round trip took over 2 s (the probe's
timeout) — ~1k concurrent PCIe read transactions starve the link that carries the payload. One
polling lane per sub-group plus a small backoff (a few hundred dependent FMAs, ~0.5 µs) is both
correct and fast (3.2 µs round trip).

## 7. Kernel *loads* from host memory are latency-bound; kernel *stores* are not

Dependent chain: 4096 sequential 32-bit reads from host memory by one lane = **258–283 µs**
(~65 ns each, ~0.06 GB/s). Spread over 4096 lanes, a 16 KiB read+write pass costs ~2–5 µs of
actual traffic. Stores to host memory are posted and effectively free at these sizes.

Consequence: **push the payload in with the copy engine (DMA), let the kernel write results back
zero-copy.** Do not design a kernel that "reads x straight out of the pinned slot" the way the CUDA
issue kernel does — the 3090 can do that at 3.9 µs, the B70 cannot.

## 8. `cudaHostRegister` refuses memory the xe driver pinned

`sycl::malloc_host` → `cudaHostRegister` fails with `invalid argument`. The other direction works
(torch `pin_memory` → `register_host_memory` → B70 kernel reads/writes it, 3090 still DMAs it).
So the **parent keeps owning and registering the handoff region**; the B70 side attaches. Do not
plan a design where the B70 allocates the shared control block.

## 9. `sysfs` PCIe link state is useless on this box

`/sys/bus/pci/devices/0000:0f:00.0/{current,max}_link_{speed,width}` reads `2.5 GT/s` × `1`
both idle and while pulling 14.4 GB/s. The switch upstream port claims Gen5 ×16, the downstream
port claims Gen1 ×1. Measure bandwidth; never infer topology from sysfs here. (`notes/bench_link.py`
style probing is the only trustworthy source, for either card.)

## 10. `sycl::ext::oneapi::experimental::clock<clock_scope::device>` is not available

Submitting a kernel that uses it fails at launch with
`Required aspect ext_oneapi_clock_device is not supported on the device`. Bounded loops in tests must
use spin budgets, not a GPU clock. Same
for `aspect::ext_intel_matrix` (the Intel-specific `joint_matrix` extras in
`doc/b70/sycl/doc/extensions/experimental/sycl_ext_matrix/`): the *documented* extension is newer
than the installed 2026.2 runtime headers, so check `__has_include` and fall back to plain
`joint_matrix` / ESIMD `xmx::dpas`.

## 11. Power baselines need the context to exist

`energy1_input` (µJ, label `card`) says 14.6 W with nothing loaded, 45.6 W with an idle-but-live
SYCL context. Utilisation figures for the port must therefore be differenced against *the same
process with the engine parked*, not against a cold card, or the resident kernel appears to cost
30 W of "utilisation" it does not have.

## 12. Never `memset`/dereference a `sycl::malloc_device` pointer from the host

Plain segfault (this config does not give the host a mapping for device allocations), which killed
two early probe runs at the first large copy. Use `queue::memset`/`memcpy`.

## 13. Toolchain notes

* `icpx -fsycl` compiles a probe in ~3 s and needs `source /opt/intel/oneapi/setvars.sh` also at
  *run* time (`libsycl.so.9` is not in the default loader path) — so a Python-driven test must be
  launched from a shell where both `setvars.sh` and `notes/env.sh` were sourced.
* `queue::flush()` does not exist in this SYCL 2020 implementation; `queue::ext_oneapi_submit_barrier()`
  is the "submit without waiting" call.
* `sycl::queue q(ctx, dev, sycl::property::queue::in_order{})` for anything that must be ordered
  (payload → flag). An out-of-order queue relies on USM-dependency inference, which does not see
  anything through a raw host pointer.
* `nd_range<1>` takes `(range<1>, range<1>)`, not two braced lists of different rank.

## 14. Repo hygiene, learned the hard way twice in one day

* **Never delete with a glob.** `rm -f probe_*[!.c]*` — intended to remove probe *binaries* — matched
  and destroyed all ten `.cpp`/`.py` sources. They came back only because every step had been
  committed minutes earlier. List the files, or `git clean -nd` first and read the output, or delete
  by exact name.
* **Verify an edit by reading the file, not the tool's echo.** Several multi-line replacements here
  looked right in review and were wrong on disk: a table row that gained a column and lost its
  neighbours, a sentence spliced mid-clause, a claim of "11/11" for a probe that prints "10/10".
  For prose and tables especially, re-read the region after editing it.
* **Commit before and after a bulk edit**, so a mistake is one `git checkout --` away rather than a
  rewrite from memory.
* **Never report a number a tool did not print.** I described the output of `plan_placement.py` —
  including "h = 99.7 %" and a capacity sweep — in prose before the script had ever run; it had a
  syntax error and a dict-unpacking bug, and every one of those figures was invented. The real run
  produced different, less convenient numbers (GLM `h` = 70.8 %, not 99.7 %). Nothing in these notes
  or in `doc/port/` may cite a measurement that is not in an `out_*.txt` next to the script that made
  it, and claims quoted in conversation must come from a finished command's output, not from an
  expectation about what it would say. This is the same failure as believing a 1580 GB/s read rate
  because it was the number the design wanted.

## 15. Bandwidth microbenchmarks lie in four specific ways

`probe_rates.cpp` reported 1580 GB/s, then 1227, then 567, then 286 GB/s for essentially the same
reads against a 608 GB/s card. Each regression was a real defect, and each one flattered or punished
the design in a different direction:

1. **Item→address mapping local to a wave.** Assigning items to tiles linearly put a wave's working
   set inside the 18 MiB L2 and returned cache bandwidth. Fix: scramble the mapping, and check that
   the *touched footprint* is orders of magnitude above cache size, not just the allocation.
2. **Counted bytes ≠ read bytes.** An item that was credited 16 tiles but read 1/8 of them inflated
   the rate ~30×. Fix: assert exact cover (every tile touched once, none out of range) *before*
   timing, and print it. `probe_rates` now does this and prints `[exact cover]`.
3. **Unconsumed loads.** Guarding the sink with `if (acc == MAGIC)` lets the compiler keep the
   arithmetic and drop the loads, or drop everything. Fix: an unconditional store into a small sink,
   plus a host-side check that the sink is non-zero ("MEASUREMENT VOID" otherwise).
4. **Shared kernel bodies across measured variants.** One kernel with `if (mode == …)` made every
   variant carry every other variant's code: the pure-read mode measured 286 GB/s specialised-
   away-into-itself and 567 GB/s when the branch was `if constexpr`. A microbenchmark whose
   instrumentation changes the result is worse than no measurement, because it looks like data.
   Fix: template on the variant, one instantiation per measured configuration.

Then, and only then, the numbers stabilised across modes and repetitions - and the surviving result
(locality worth up to ~1.7–2.0×, layout worth nothing reliable, arithmetic worth a few percent)
reversed two conclusions the earlier, smoother-looking numbers had supported.

## 16. A proxy metric must be the same *kind* of quantity as the thing it proxies

Needing a churn number for the migration policy and having only cumulative expert-count profiles, I
tried two proxies and both produced confident, useless figures:

* comparing the top-N **sets of counts** between groups of layers reported "92 % overlap". The sets
  were of *values*, and decayed counts repeat (many experts share 16.046875), so the intersection
  measured value collisions, not whether the same experts were hot.
* splitting one layer's array in half reported "100 % overlap". That partitions experts by index: a
  spatial split of a static snapshot, with no time in it at all, and the same value-collision artifact
  on top.

Both were rejected before reaching the plan, and the honest state is now written where the number is
used (`doc/port/b70-architecture.md` §4a: churn unmeasured, the two thresholds coinciding at
~0.3 %/token, E11 to produce it from two snapshots or per-window counters). The lesson generalises to
every statistic scraped from someone else's artifact: ask what the *identity* of the compared objects
is, and whether the artifact has the axis (here, time) the question needs. A decayed cumulative count
cannot answer "how fast does the set change", no matter how neatly the numbers line up.

## 17. An absolute microbenchmark rate is not a constant; sweep the working set before quoting one
`probe_rates` measured the *same* kernel on the *same* geometry at six working-set sizes and returned
132–292 GB/s (Qwen3.8) and 132–260 GB/s (GLM) — a ~2× swing, non-monotonic, with no clean relation to
grid size (128 MiB: 104,800 items at 200 GB/s; 64 MiB: half the items at 292). The first version of
the design docs quoted "287–313 GB/s" as if it were a property of the card, when it was a property of
the card *plus* a 1536 MiB footprint I had not thought about.

Three rules came out of it:

* **Quote rates as a bracket with the footprint attached**, and take design numbers from the regime
  the real workload sits in, not from wherever the probe happened to land.
* **Ratios between modes survive; absolutes do not.** Across three independent runs, absolute rates
  repeat to 0.1–2.4 % but every mode-ratio repeats to ≤3 %, and the ratios are what the design
  conclusions rest on.
* **Check that the effect you are measuring is bigger than the instrument's variance.** Banded-vs-
  native came out at 0.96–1.05× while footprint noise alone is ~2×, so the correct claim is "no
  reliable gain", not "worth nothing". Overstating a null is the mirror image of overstating a win.

## 18. An unrecognised flag is parsed as data

`./probe_rates --quick` did not select a quick mode (there is none): `atoi("--quick")` is 0, which is
a valid shape index, so the probe silently measured *one* geometry while I believed I had a sweep. It
surfaced only because the output had one block where three were expected. The probe now rejects
arguments that are not a shape index and prints the shape table. Generalise: any tool whose arguments
are integers must validate them, because the failure mode is a plausible result, not an error.

## 19. Match the measurement's condition to the workload's operating point (`topk`, batch, `h` — not the checkpoint)

Every decode estimate in the plan was built by asking "what GB/s does the card sustain?" and multiplying.
The question that decides the answer was never asked: **what is the working set of the thing being timed?**
Per token only `topk` of E experts fire, so one MoE layer reads `topk × expert_bytes`, times the fraction
`h` this card owns — **14.3 MiB** for Qwen3.8 at b=1, **50.9 MiB** for GLM. That is 2 orders of magnitude
below the 1–2 GiB sweeps the rates came from, and since the measured curve moves ~2× over exactly that
range, the old numbers were not conservative or optimistic in a predictable direction: they were sampled
at the wrong x. Recomputed at matched footprints, Qwen3.8 gets *better* (51 µs/layer, not 55–95) and GLM
gets much *worse* (405 µs/layer, not 278–548), which flips the practical recommendation for the model
that matters most.

Three siblings of the same mistake, all found only after writing the first version down:

* **`topk` was guessed.** Qwen3.8 is 10, GLM is 8; the script had 8 for both because the number came from
  my memory of `doc/prep` instead of from `config.json`. Now read from the checkpoint.
* **Batch was treated as a constant.** Distinct experts per layer grow almost linearly with rows (10 → 39
  → 73 for Qwen3.8 at b = 1 → 4 → 8), so offloaded work scales ~9× while the parent's window — bound by
  weight reads at b=1 — barely moves. "The offload hides at decode" is a b≤4 statement dressed as a
  general one.
* **Parallel workers were summed.** The homes compute concurrently, so per-layer latency is
  `max(T_parent, T_b70/N, T_cpu)`; adding worker ms/token (17.0 + 19.6 ms for GLM) implies 27 tok/s when
  the max-based figure is 51 with one card and 79 with two — and shows that a third card buys exactly
  nothing. Every capacity recommendation must be built on the max, or it argues for hardware that cannot
  help.

The general rule these probes should have enforced on themselves: before multiplying a measured rate by a
quantity, verify that the measurement was taken *at that quantity*.

## 20. A proxy that omits the operation under study cannot bound its cost

For most of this design's life, "decode is bandwidth-bound, arithmetic costs 1–4 % of bandwidth, the
int8 dot's instruction count does not matter" was a *measured* conclusion. It rested on `probe_rates`,
which walked the real trellis bytes at ~1 lane-op per weight and varied an artificial arithmetic density
on top. Then `probe_gemv` ran the actual operation — checkpoint trellis bytes, the `moe_mul1.h` identity,
output bit-exact against `tests/testlib/trellis.py` — and returned **27.9 GB/s**, then 61.4 GB/s after
adopting the byte-sum dot, against 292 GB/s for the bare stream. An instruction-count model (256 EU ×
2.8 GHz × 2 slots) predicts 31.6 and 67.2 GB/s from the two kernels' op counts, so the card was never the
question; the proxy was.
